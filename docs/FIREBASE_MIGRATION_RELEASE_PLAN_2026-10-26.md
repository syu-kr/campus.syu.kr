## 유지할 계약과 제외할 작업

- 시간표의 모든 원본 검색 조건·선택값·최대 4안·겹침 검증·공유·초안, 졸업요건의 원본 선택지·종속 초기화·계산·저장 복원을 유지한다.
- `syu-campus-timetable-draft-v1`, `syu-campus-graduation-self-check-v2`, Meet의 기존 키·형식·TTL을 유지한다. 같은 운영 origin의 저장값이 이어져야 한다. 다른 로컬 포트나 Preview의 저장값 자동 이전은 요구하지 않는다.
- 공지 원문 링크, 인라인 AI 요약, URL 검색·페이지·언어·목록 복귀, 정상적인 사각 시간표·달력·좌석 격자를 유지한다.
- 문의·룸메이트·일정 방·개인 메모는 공개 데이터 이전이나 Google 번역 대상에 포함하지 않는다. 기존 비활성 기능을 활성화하지 않는다.
- 이번 출시 범위는 웹을 기본으로 계획한다. Android 스토어 새 출시는 별도 빌드·서명·실기기 검증이 필요하다.
- Markdown 운영 가이드, 소스 코드, i18n 사전, 교육과정 감사 원본 `data-source/`는 콘텐츠 DB 이전 대상에서 제외한다. 공개 JSON별 관리자 편집기를 새로 만드는 작업도 별도 기능이다.
- Motion 도입·새 UI 라이브러리·전체 상태 관리 교체·일괄 컴포넌트 분해는 계획에 넣지 않는다. 확인된 오류와 이전에 필요한 공통 경계만 수정한다.

이번 독립 검증의 확정 결함을 재현 조건과 함께 작은 수정으로 처리한다. 로딩·선택창 애니메이션 도중의 순간 측정, 모의 응답이 빠진 테스트, 외부 공급자 장애는 제품 결함과 구분한다.

수정마다 영향받는 공통 컴포넌트의 사용처를 먼저 찾고, 같은 상태의 데스크톱·모바일을 다시 검사한다. 검색·Select·모달은 키보드와 초점 복귀를 포함한다. 영어 문구 길이·원문 fallback·번역 재시도는 한국어 화면과 함께 검사한다. 모바일에서 숨기는 기능이 있다면 접근 가능한 대체 경로가 실제로 있는지 확인한다.

완료 조건은 확정된 출시 차단 결함 0개이며, 경미한 항목을 남길 경우 사용자 영향과 재검사 조건을 명시한다. 자동 가로 넘침 0개만으로 UX 완료를 판정하지 않는다.

## B 환경과 실제 연결

### Storage

1. 기존 버킷 이름·프로젝트 일치·리전·요금제·서버 서비스 계정 권한을 읽기로 확인한다. `MANAGED_CONTENT_STORAGE_BUCKET` 우선, `NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET` fallback이라는 현재 코드 계약을 유지한다.
2. `lib/server/managed-media.ts`와 관리자 업로드 API를 통해 개인 정보 없는 합성 이미지 1개를 업로드한다. 테스트 파일은 새 UUID를 쓰며 기존 파일을 덮어쓰지 않는다. 실제 쓰기 대상과 정리할 객체 경로를 실행 전에 고정한다.
3. WebP 변환·크기·EXIF 제거·공개 `/api/content-media/[id]` 200·Content-Type·ETag 조건부 요청·오류 응답을 확인한다. 관리자 화면의 미리보기, 모바일 이미지 대체, 영어 alt 표시도 검사한다.
4. 미인증/비관리자 요청 거부와 잘못된 형식·용량의 실패는 모의/격리 데이터로 먼저 검사한다. 실제 파일 조회 성공을 실제 관리자 권한 검증의 대체 증거로 쓰지 않는다.
5. 생성한 시험 객체만 경로·generation을 대조해 정리하거나 검증용 보존 대상으로 명시한다. 버킷 전체나 기존 업로드를 정리하지 않는다.

버킷 메타데이터 조회 성공은 업로드 권한 성공과 다르다. 서버 Admin SDK 권한과 브라우저 Storage 규칙을 구분하며, 공개 쓰기를 열어 해결하지 않는다. 업로드 이미지는 게시 전에도 URL로 접근 가능하다는 현재 정책을 유지한다. 버킷 이름은 프로토콜 접두어 없이 사용한다. [Firebase Admin Storage 안내](https://firebase.google.com/docs/storage/admin/start)

### 번역과 운영 환경

- 키·Admin 인증·요청 제한 비밀값의 존재, API 제한, Preview/Production 적용 범위를 확인한다. 비밀값을 문서·PR·브라우저에 출력하지 않는다.
- `public_content_translation_fields`, `public_content_translations`, `public_content_translation_usage`의 `expires_at` TTL 정책과 Timestamp를 확인한다. 기존 다른 collection group의 보존 정책은 바꾸지 않는다. TTL은 즉시 삭제가 아니므로 코드의 만료 검사도 유지한다. [Firestore TTL](https://firebase.google.com/docs/firestore/ttl)
- 앱 기본 25,000자/UTC일 한도, Google quota, 예산 알림을 함께 기록한다. Google 일일 quota의 Pacific Time 초기화와 앱 UTC 초기화를 혼동하지 않는다. 예산 알림을 자동 과금 차단으로 간주하지 않는다. [Cloud Translation 할당량](https://docs.cloud.google.com/translate/quotas)
- 실제 번역을 반복 과금하며 전수검사하지 않는다. 기존 실제 성공 증거를 활용하고 새 학사 용어·긴 본문·숫자 포함 문구만 정한 문자 예산 안에서 표본 검토한다. 일반 UI 실패 테스트는 mock으로 수행한다.
- 완료 후 `ADMIN_CONTENT.md`의 설정 전 버킷 404 기록에는 설정 후 확인 결과를 덧붙인다. 성공하지 않았는데 오래된 기록만 지우지 않는다. TTL 설정값은 `FIRESTORE_RULES.md`와 `CONTENT_TRANSLATION.md`가 서로 일치하게 정리한다.

## C 서비스 공지 이전

### 코드 변경 범위

`types/managed-content.ts`, `lib/serviceNotices.ts`, `lib/server/managed-content.ts`, `lib/server/public-managed-content.ts`, 관리자 API/편집기, 공개 목록/상세, `app/sitemap.ts`, 번역 source resolver와 관련 테스트가 대상이다. importer는 기존 parser·검증 함수를 사용하며 새로운 Markdown parser나 CMS를 도입하지 않는다.

현재 관리 저장본은 원문 번호·작성자·날짜·언어를 Markdown 기본본에 의존한다. 특히 `012-english-version-beta`는 영어 원문이다. 이 의존성을 제거하지 않고 Markdown을 삭제하면 작성자가 기본값으로 바뀌고 번호·언어가 달라질 수 있다.

### 보존할 정보

| 정보 | 이전 규칙 |
| --- | --- |
| slug·공개 번호 | 기존 URL과 `019` 같은 표시 번호를 그대로 저장. 새 DB ID로 바꾸지 않음 |
| 최초 날짜·작성자·원문 언어 | 원본 값을 불변 메타데이터로 유지. import 시각을 게시 날짜로 쓰지 않음 |
| 제목·요약·Markdown 본문 | 링크·코드·본문 구조 포함 동일. 자동 문장 수정·새 요약 생성 금지 |
| 검수 영문 | 유효 원문 hash 대조 후 18개 매칭. 영어 원문 012도 그대로 보존 |
| draft·published·revision | 이미 관리자가 수정한 DB 레코드와 미게시 초안은 보존 |
| 중단·보관 | 숨김 상태/tombstone 유지. 기본 MD를 다시 노출하지 않음 |
| 번역 검수 해시 | 원문 전체 LF 정규화 SHA와 CMS `[title,summary,content]` 해시를 각각 검증. 서로 같은 값이라고 취급하지 않음 |

### importer와 전환 절차

1. 19개 원문·18개 영문과 관련 DB 레코드만 읽어 백업·manifest를 만든다. 파일 hash, ID, 기존 DB revision/updateTime, 언어 매칭을 기록하고 비공개로 보관한다.
2. 기본 동작은 dry-run으로 한다. 출력은 `신규/동일/기존 수정으로 보존/충돌/검수 영문 불일치` 건수이며 본문·개인 정보·자격증명은 출력하지 않는다.
3. 신규 데이터만 조건부 생성한다. 기존 레코드의 메타데이터 보충이 필요하면 기대 revision/updateTime을 확인하고 게시 내용·초안을 그대로 둔다. 충돌을 force 덮어쓰기로 처리하지 않는다.
4. 격리 환경에서 최초 import, 같은 import 재실행, 중간 실패 후 재개, 동시 관리자 편집을 검사한다. 동일 재실행은 쓰기 0건이어야 한다.
5. DB reader만 사용한 상태로 원본과 비교한다. 목록 순서·번호·날짜·작성자·본문·영문·404·페이지 복귀·홈 공지·sitemap·SEO를 비교한다. MD fallback 때문에 통과한 것을 이전 성공으로 세지 않는다.
6. 실제 이전 시 짧은 편집 정지 구간을 정하거나 조건부 쓰기로 충돌을 차단한다. 게시 중단 항목이 살아나지 않는지 대조한 뒤 DB 원본을 활성화한다.
7. 원본 MD는 삭제 전에 백업과 되돌리기 검증을 마친다. 앱에서 파일 접근을 제거한 빌드와 DB 조회가 성공한 뒤 별도 정리 커밋으로 제거한다.

롤백은 importer가 만든 레코드 및 이전 이후 변경 여부를 대조해 수행한다. 이후 관리자가 수정한 레코드는 과거 백업으로 일괄 복원하지 않는다. 게시 중단·보관 정보가 적용되지 않는 옛 앱으로 되돌리는 것도 안전한 롤백으로 보지 않는다.

## D와 E 공개 JSON 이전

공개 JSON은 Storage의 불변 버전 파일로 두고 Firestore에는 활성 버전과 manifest 위치 등 작은 메타데이터만 둔다. 기존 SHA256·size·schema·출처 상태·7개 버전 보존 계약을 재사용한다. 큰 JSON을 Firestore 한 문서에 넣지 않는다. 현재 가장 큰 파일은 3,767,544B이며 Firestore 문서 한도는 1MiB다. [Firestore 제한](https://firebase.google.com/docs/firestore/quotas)

| 묶음 | 파일 수 | 구현 시 주의점 |
| --- | ---: | --- |
| 일일 공지 6종·학식·AI·공휴일 | 9 | 현행 `DAILY_CRAWL_DATA_FILES`·Pages manifest 계약. 공모전과 AI도 같은 버전 사용 |
| 전화번호·학사 일정 | 2 | 현재 월간 작업이 Git PR을 생성함. 검토 단계 유지 후 승인된 snapshot만 활성화 |
| 꿀팁·셔틀 시간표·특별 운행 기간 | 3 | 수동 편집/검토, 정렬·분류·날짜·공휴일 조건 및 도서관의 운행 기간 참조 유지 |
| 졸업요건·교육과정·선택 규칙·출처 | 8 | 2025/2026 자료와 근거 유지. 동기 import·계산 의존 해소 후 이전 |

`data-source/curriculum/`의 감사 자료는 이 22개와 다르다. 만나의집의 `cafeteria/student-restaurant-1.json`은 별도 Pages 발행 작업이 있으므로 위 22파일 외의 추가 이전 대상으로 D에서 함께 목록화한다. 원문 이미지 해시·검수 입력·성공한 수집만 캐시하는 계약과 주차/재료 검증을 유지하면서 같은 버전 발행 경로로 연결한다. 현재 설정된 공개 식단 URL의 호환성도 검사한다. 날씨·실시간 버스·도서관·강의 조회 API의 원본 서버를 Firebase 데이터로 대체하지 않는다.

### 공통 reader와 writer

1. 모든 소비자를 목록화한다. 앱 API/SSR/클라이언트 fetch뿐 아니라 Google 번역 원문 resolver, sitemap, IndexNow, 크롤러 입력/출력, Python 감사·생성 스크립트, build tracing, 테스트 fixture까지 포함한다.
2. 기존 `lib/server/crawl-data.ts`, `lib/crawl-data-contract.ts`, `scripts/publish-crawl-data.ts`에 필요한 저장소 경계를 추가한다. 서로 다른 파일 스키마를 무검증 범용 JSON API로 합치지 않는다.
3. writer는 새 버전의 모든 파일을 먼저 업로드하고 size/hash/schema/필수파일을 검사한다. 그 후 기대 이전 버전을 확인하는 트랜잭션으로 활성 버전을 한 번에 바꾼다. 중간 업로드는 공개 원본을 바꾸지 않는다.
4. reader는 manifest를 고정한 뒤 해당 버전만 읽는다. 요청 중 새 파일과 옛 파일을 섞지 않는다. 서버 cache·ETag·타임아웃·크기 상한·허용 경로 검사를 유지한다.
5. 수집 일부 실패는 기존 유효본과 sourceHealth를 보존한다. 전체 실패를 빈 목록 성공으로 발행하지 않는다. DB 관리 공지의 게시 중단과 달리, 수집 자료는 검증된 이전 snapshot으로 복구할 수 있다.
6. GitHub Actions의 일일·월간·만나의집 발행, 롤백, IndexNow를 함께 변경한다. 현재 IndexNow가 `x-crawl-data-source: github-pages`와 Pages current manifest를 확인하므로 헤더만 바꾸면 검증이 실패한다. 새로운 활성 버전과 실제 서비스 응답을 대조하게 바꾼다.
7. 이전 초기에는 현재 Pages/번들 원본을 보존하고 새 저장소 응답과 shadow 비교한다. 새 저장소를 활성화한 뒤에는 writer를 하나로 확정하여 서로 다른 최신 버전이 생기지 않게 한다. 무기한 이중 쓰기는 만들지 않는다.

### 졸업요건과 빌드 의존

`lib/graduation.ts`와 `GraduationPageClient.tsx`는 JSON을 동기 import한다. 동일한 평가 함수를 입력 snapshot으로 실행하도록 좁게 조정하고, 서버에서 검증한 묶음을 초기 화면에 전달하는 구성을 우선한다. 초기 선택지를 빈 값으로 표시한 뒤 저장된 학과를 지우는 흐름이 생기면 안 된다.

선택지·순서·중복·학점·입학연도·학과별 규칙·출처를 원본 fixture와 대조한다. 로딩·실패·재시도 중 저장값을 보존하고, 새 참조 자료가 기존 저장 학과를 지원하지 않으면 조용히 초기화하지 않는다. 사용하는 자료 버전과 호환되지 않는 앱은 활성화하지 않는다. 같은 검증 snapshot을 빌드/테스트에서 재현할 수 있어야 하며, credential 없는 CI가 임의 최신 원격 자료에 의존하지 않게 한다.

### 전환과 복구 완료 조건

- 22개 각각 `이전/유지 이유/소비자/생산자/검증기/전환 증거`를 기록한다. 한 묶음 성공을 전체 완료로 확장하지 않는다.
- 성공본·누락파일·hash 불일치·깨진 JSON·권한 오류·네트워크 timeout·부분 업로드·동시 발행·이전 버전 복귀를 검사한다.
- 기존 public JSON URL 소비자가 있으면 같은 URL/API 응답을 유지하거나 명시적 호환 경로를 제공한다. 파일 삭제로 설치 앱·외부 링크를 깨뜨리지 않는다.
- 앱 배포와 무관하게 활성 데이터 버전만 이전 정상본으로 되돌릴 수 있어야 한다. 삭제 후보 버전은 활성/복구 대상에서 제외했는지 확인한다.

## F 최종 회귀와 릴리스 후보

### 기능과 UI

37경로 × KO/EN × 1440/390px의 148개 기본 화면을 최종 후보에서 검사한다. 동적 공지 상세와 인증 관리자 편집, 실제 쓰기는 별도 시나리오로 집계한다. 대표 화면은 320·768·899/900·1920px, 200% 확대, reduced motion을 추가한다.

검색 즉시 메뉴/공지 제출/뒤로가기, 공지 원문/AI/페이지 끝, 시간표 모든 필터/4안/충돌/복원, 졸업 종속 선택/검증/초기화, 문의 오류와 값 보존, 배너 예약/중단/오늘 숨김, 관리자 편집 충돌/권한 상실, 영어 원문 복구/재시도를 검증한다. 실제 Safari·Android/iOS 키보드·스크린리더·PWA는 자동 Chromium 검사와 별도로 남긴다.

### 성능과 비용

- 이전 전후 같은 빌드 모드·Node·데이터 버전·리전·기기 조건에서 홈/공지 목록/상세/졸업요건/영어 첫 진입을 측정한다. 각 조건 최소 5회와 원시값을 보관한다.
- 브라우저 HTTP cache, 서버 cache, 번역 cache의 cold/warm을 각각 기록한다. Playwright routing으로 cache가 꺼진 재방문을 warm cache로 부르지 않는다.
- TTFB·LCP·CLS·조작 응답·전송량·요청 수·DB 읽기·Storage 다운로드·신규 번역 문자 수를 비교한다. 반복 요청의 캐시 재사용과 영어 개인 입력 전송 0건을 확인한다.
- 임시 회귀 기준: 같은 조건에서 중앙값이 20% 이상이면서 200ms 이상 악화되면 원인 해결 또는 범위 축소 후 재측정한다. 이는 이번 프로젝트의 제안 기준이며 공식 성능 표준이 아니다.
- 운영에서는 모바일/데스크톱 각각 p75 LCP ≤2.5초, INP ≤200ms, CLS ≤0.1을 목표로 관찰한다. 로컬 5회나 TBT로 실제 INP/CWV 통과를 주장하지 않는다. [Web Vitals 기준](https://web.dev/articles/vitals)

### SEO와 공개 저장소

공지 이전 전후 slug·날짜·작성자·canonical·hreflang·Article 언어·OG·본문 초기 HTML·사이트맵 수와 URL 집합을 비교한다. DB 신규 공지·예약/종료·보관·404도 검사한다. 브라우저 자동 영어 교체를 서버 영문 SEO 완성으로 세지 않는다. 사이트맵과 IndexNow에는 비공개·검색 결과·개인 방이 섞이지 않아야 한다.

공개 준비는 신규/변경 파일의 비밀값·개인 PC 경로·캡처·계정 식별자·데이터 권리·라이선스 및 관련 Git 이력을 검토한다. `.env`, 백업, HAR, 인증 세션은 올리지 않는다. 오래된 아이콘은 설치 앱·알림·외부 참조와 롤백 기간을 확인한 뒤 정리한다. 현재 쓰이지 않는 것처럼 보인다는 이유만으로 제거하지 않는다.

### 커밋과 검사

현재 222개 작업 항목을 파괴적으로 되돌리거나 한꺼번에 stage하지 않는다. 기존 M3/SEO·영어·관리자 변경의 의존 관계를 확인하고, 이후 UI 보완 / 공지 importer / snapshot 전환 / 검증·문서 정리를 검토 가능한 커밋으로 나눈다. 이미 구현된 공통 타입을 공유하는 변경을 억지로 독립 PR로 잘라 빌드를 깨뜨리지 않는다.

후속 구현에서는 각 변경의 타입 검사와 관련 테스트를 먼저 실행한다. 최종 후보에서 저장소 지정 npm 10.9.4와 Node 22.22.2 기준으로 다음 게이트를 수행한다.

```text
npm ci
npm audit --audit-level=moderate
npm run check
```

`check`는 lint·타입·i18n·TWA 정적·unused·Python·졸업/교육과정·crawl dry-run·unit·build를 포함한다. CI의 Python audit, CodeQL, Dependency Review도 최신 head에서 확인한다. 리소스 경합을 줄이기 위해 전체 단위 검사와 빌드를 동시에 실행하지 않는다. 수정 후 옛 SHA의 성공 결과를 재사용하지 않는다.

## G 실제 이전과 출시

**현행 `sync-to-vercel-repo.yml`은 main CI 성공 뒤 Vercel 저장소로 동기화한다. 따라서 배포를 보류하는 동안은 squash merge도 보류한다.** 자동화 설정을 임의로 끄거나 병합부터 해 두지 않는다. 실제 원격 workflow 상태는 출시 직전에 다시 확인한다.

실행 순서는 다음과 같다.

1. importer dry-run·백업·충돌·비교 보고서, 전환할 데이터 버전, 이전 정상 앱/데이터를 준비한다.
2. 호환 reader가 준비된 상태에서 데이터를 복사한다. 복사만으로 공개 원본을 바꾸지 않는다. 기존 운영 앱의 읽기 계약과 맞는지 확인한다.
3. 변경이 격리 환경에서 검증된 PR head인지 재확인한다. 실제 쓰기/전환/출시 승인 범위를 확정한 뒤 업무 데이터 이전을 실행한다.
4. 최종 PR head와 base·필수 검사를 다시 확인하고, 승인된 출시 시점에 squash merge한다. main 새 SHA의 CI와 sync 결과를 확인한다.
5. 앱 source SHA → mirror SHA → Vercel deployment → 공개 `indexnow-deployment.json.sourceSha`를 연결한다. 해당 앱이 지원하는 데이터 버전만 활성화한다.
6. 운영 도메인에서 공개/인증 조회·SEO·OG·sitemap·실제 API·이미지·영어·CSP를 검사한다. 허용한 테스트 대상만 쓰기/수신 확인 후 정리한다.
7. 다음 정상 수집 주기에 파일 발행과 active version을 확인한다. 초기 오류율·429·읽기량·번역량을 보고, 안정 확인 후 옛 파일/전환용 fallback을 별도 제거한다.

페이지 오류·데이터 불일치·잘못된 공개·핵심 선택값 손실이 재현되면 전환을 중단한다. 앱·데이터 활성 버전·DB 기록·환경값을 각각 복구하며 앱 rollback만으로 DB가 복구됐다고 하지 않는다. 외부 셔틀 원본 장애는 별도 미해결 항목으로 기록하고 정적 시간표 대체가 유지되는지 확인한다.

## 예상 작업량과 다음 실행 단위

다음은 개발자 1명 기준의 대략적인 순수 작업량이다. 외부 설정·검토·실기기 확보·CI 대기·문제 재현 시간은 별도이며 완료 시각 약속이 아니다.

| 작업 묶음 | 예상 |
| --- | --- |
| UI 확정 결함·환경/Storage 확인 | 0.5–1.5일, 결함 규모에 따라 조정 |
| 서비스 공지 메타데이터·importer·리허설 | 1–2일 |
| 공개 JSON reader/writer·졸업 계산 의존·자동화 이전 | 2–4일 |
