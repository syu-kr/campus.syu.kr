# 셔틀 도착예상 실측 및 공개 절차

**첫 실측 구간: 석계역 4번 출구 출발 → 태릉입구역 7번 출구 도착.** 독립 검증 전에는 실제 차량에 숫자를 붙이지 않는다. 운영 도메인에서 주소로만 여는 `/campus/bus-info/preview`가 시험 대상이다. 정식 페이지·메뉴·사이트맵에는 추가하지 않는다. 주소는 접근 통제가 아니므로 기록 쓰기·원자료 접근은 별도로 보호한다.

운영 미리보기에서 ‘실측 수집·계산 점검’을 연다. 관리자로 로그인하고 ‘수집 시작’을 누르면 그 탭에서 분당 한 번 서버 수신 자료를 기록한다. 닫거나 중지하면 끝나며 상시 백그라운드 수집기는 아니다. 수집 주소와 인증값은 서버 실행 환경에만 둔다. 토·일은 예외 시간표가 있어도 조회·저장하지 않는다. 평일에는 공휴일/운휴·미확정·시간표 밖·확인되지 않은 간격운행을 제외하고, 노선별 첫차~막차 사이에 최근 20분 내 출발이 있는 경우만 수집한다. 새 응답·해당 노선 차량이 없으면 기록을 만들지 않는다. 한 분에 여러 탭이 열려도 문서는 한 개다. 운영 외 환경은 실제 저장하지 않는다. ‘시험 입력으로 계산 확인’은 저장소에 접근하지 않고 배포된 계산기의 4분 산출과 만료를 점검한다. 예시 재생 역시 저장하지 않는다.

## 현장에서 바로 시작하기

1. **운영 담당자**가 여객 운행 여부·방향·정류장·회차를 확인한다. 같은 학교여도 학교 출발과 학교 도착의 방문 ID는 다르다. [방문 ID와 순서](../../lib/shuttle-visits.ts)의 배열 인덱스가 0부터 시작하는 `visitSequence`다. 경로가 바뀌면 새 `shape`를 발급한다. 학교→화랑대는 별도 우회로 조사하며 학교행 기록으로 합치지 않는다.
2. **동승 관측자**가 자동 시각을 켠 휴대폰으로 [빈 현장 기록표](field-visits.csv)를 복사해 매 사건을 한 줄로 기록한다. 기사에게 기록 조작을 맡기지 않는다. `arrival`은 실제 지정 지점에서 승하차 가능한 순간, `departure`는 그후 실제 움직이기 시작한 순간이다. 무정차 통과는 `pass`, 놓친 사건은 `missed`다. 시각은 초와 시간대까지(예: ISO 8601의 +09:00), 오차는 초로 남긴다. 시간 미상은 비워 두며 실제 0초로 바꾸지 않는다. 학교 출발은 출발 사건만, 종점은 도착 사건만 있어도 된다.
3. **수집 담당자**가 운행 중인 차량의 위치를 별도로 기록한다. 장치가 제공한 위치 측정시각, 우리 수신시각, 정확도(m), 위경도, 무작위 차량·회차 키, 경로 버전을 비공개 원장에 저장한다. 기존 위치 API가 측정시각을 제공하지 않으면 운영자 허가를 받은 동승 단말에서 차량 운행 중에만 GPS를 수집한다(파일럿 목표 5~15초). 두 시계를 동기화하고 단말의 실제 측정 주기·단절·터널·오차를 확인한다. 브라우저 조회시각, 시간표상 출발, 외부 사이트 분 단위 감지 이력은 실측을 대체하지 않는다.
4. **수집 일정**은 평일 혼잡/한산 시간대를 모두 포함하고 서로 다른 금요일 최소 3일을 확보한다. 석계 첫 구간 이후 태릉→학교, 석계 전체 순환, 화랑대→학교, 별내 양방향 순으로 넓힌다. 동승 관측 외에도 일부 날짜는 정류장 관측자와 출구·시각을 대조한다. 학기·방학·온라인 주간은 분리한다. 날짜 수가 부족하면 기간을 연장한다.

개인 이름·학번·승객 사진·차량 번호판은 받지 않는다. 비공개 수신 기록은 일자별 차량 가명과 함께 `shuttle_pilot_receipts`에 저장한다. 30일 만료를 설정하고 기존 일일 정리 작업에서 삭제한다. 원본 이름·차량 ID·운영자 UID는 저장하지 않는다. 수신시각만 있으면 `measuredAt:null`로 남긴다. 이 자료만으로는 실제 도착·출발을 알 수 없어 동승 관측과 대조해야 한다.

## 계산기 입력 만들기

- 같은 여객 회차·경로·연속 방문에서만 `다음 arrival − 현재 departure`를 주행시간으로, 같은 방문의 `departure − arrival`를 정차시간으로 쓴다. 누락, 통과, 저품질, 음수, 중복, 회송, 다른 출구를 건너뛰어 채우지 않는다. 오래 걸렸다는 이유만으로 정체 표본을 제거하지 않는다.
- 기준 모델은 같은 구간·운행 유형의 실측 중앙값이다. 개선 후보는 한국시각 개별 요일 × 구간 진입 30분대 중앙값이다. 서로 다른 날짜 3일·표본 30건 미만 셀은 같은 구간의 승인된 기본 중앙값으로 돌아간다. 정확도가 입증된 셀만 넣는다. 돌발정체의 실시간 보정은 아직 사용하지 않는다.
- **위치 매칭 담당자**가 동일 회차의 연속 측정점을 방향 있는 도로선에 투영한다. 마지막 확인 방문, 거리 진행, 정확도와 이탈 거리, 도로가 겹치는 곳의 방향을 현장 정답과 replay해 허용 오차를 정한다. 일치하지 않거나 후보가 여럿이면 `match:"verified"`를 발급하지 않는다. 단일 위경도, GPS에서 움직이지 않는다는 이유만으로 여객·정차를 확정하지 않는다. 파일럿의 출발 사건만으로 경로 전체의 진행률을 만들어 내지 않는다.
- 운영용 위치 수집기는 **신뢰된 서버에서만** Firestore `shuttle_eta/current`의 `runs` 배열을 매 수신 주기에 원자적으로 **교체**한다. 하루에만 유효한 차량 가명과 회차별 키를 쓴다. 운행 종료·회송·이탈·단절 시 해당 행을 제거한다. 동시에 활동하는 10대 이하, 한 차량/회차당 최신 한 행만 보낸다. 오래된 비동기 쓰기가 새 상태를 덮지 않도록 수집기는 한 작성자 또는 단조 증가 버전과 트랜잭션을 사용한다.

| 최신 운행 입력 | 단위·의미 |
| --- | --- |
| `vehicleKey, runId, passenger, match` | 차량 가명, 확정된 회차, 여객 운행 여부, 검증된 방향·도로 매칭 여부. 내부 전용 |
| `route, shape, serviceDate, pattern` | `seokgye` 등 노선 변형, 실제 사용한 도로 버전, KST YYYY-MM-DD, [서버의 적용 시간표 키](../../lib/server/shuttle-eta.ts). 예: 일반학기 월~목은 `mondayToThursday`, 온라인 주간에는 해당 공지 ID도 붙는다 |
| `from, phase, fraction` | 현재 구간 시작 방문 ID, `moving` 또는 `dwelling`, 구간 도로 누적거리 진행률 [0,1). 정차는 0. 구간 끝은 다음 방문이 확인된 뒤 갱신 |
| `enteredAt, measuredAt, receivedAt` | UTC epoch **밀리초**. 현재 이동 구간의 실제 진입시각(정차면 실제 도착시각), 단말이 측정한 시각, 서버가 받은 시각. 수신·조회로 측정시각을 갱신하지 않는다 |
| `departures` | 고정 대기가 있는 방문 ID → 해당 회차의 확정 출발 UTC 밀리초. 없으면 그 지점 너머의 예측을 보류 |

일반 차량 좌표 API는 그대로이고 이 입력 계약을 충족하지 않는다. 현재 공개 수치의 원천은 위의 사설 문서와 코드 리뷰를 거친 모델뿐이다. 공용 쓰기 API나 클라이언트 쓰기 권한은 열지 않는다.

## 언제 처음 공개하나

1. **섀도 모드:** 수집 성공 여부와 독립된 30초 시각 격자에서 당시 *이미 수신된* 자료만 [같은 계산기](../../lib/shuttle-eta.ts)에 재생한다. 후보 모델은 오프라인에서 평가하며 운영 레지스트리에 넣지 않는다. 공개 게이트를 순환 검증하지 않도록 후보 생성은 아래 순수 계산 함수로 하고, 실제 점수로만 공개 여부를 정한다. 예측 로그에는 회차·시도시각·목표 방문·모델 버전·예측시각 또는 보류 사유를 남긴다.
2. **독립 평가:** 날짜·회차 순으로 학습 → 보정 → 마지막 두 주 검증으로 고정한다. 모델을 바꿨으면 새 검증 날짜가 필요하다. 방향당 독립 회차 최소 10개(목표 20개 이상), 금요일·혼잡·비혼잡을 확인한다. 현재 구간/정차 여부에서 특정 목적 방문까지의 전체 오차를 검증한다. 원시 폴링 수를 독립 회차 수로 세지 않는다.
3. **공개 기준:** 정답까지 0~10분이면 평균 절대오차 ≤90초, 절대오차 P90 ≤180초, 10~20분이면 ≤120초·≤240초. 가용률 ≥90%, 잘못된 방향·회차·통과·휴일·오래된 위치 안내 0건. 가용률 분모에는 예측이 없던 점도 포함한다. 예측별 오차와 정류장 방문별 오차, 일찍 안내한 오차, 금요일·혼잡 구간을 따로 본다. 해당 범위의 정답 표본이 없으면 그 범위는 보류한다.
4. **활성화:** 비식별 검증 보고서를 저장하고 [공개 모델 목록](../../lib/server/shuttle-eta-releases.ts)에 구간 순서, 통계, 경로 버전, 운행 유형, 출발 상태, 대상 방문, 유효 날짜·진입 요일·시각과 보고서 경로·검증 점수를 코드 리뷰로 등록한다. 예를 들어 화요일 15~17시에만 검증했다면 `entryWindow`는 요일 2, 시작 900, 끝 1020(미포함)으로 제한한다. 같은 범위에 중복 모델을 등록하지 않는다. 한 구간 통과는 인접 구간이나 다른 시간표를 승인하지 않는다. 공개 전 실수신 자료를 사용한 staging 점검 → 정식 배포 → 같은 노선에서 API와 정식 화면을 대조한다. 최초 운영 목록은 비어 있다.
5. **중단:** 원천 측정 후 90초가 지나거나 예측 시각이 지나면 재수신 전이라도 브라우저에서 숫자가 사라진다. 장애 시 캐시된 숫자를 재사용하지 않는다. 중대한 방향·회차 오류가 나오면 수집기가 해당 운행을 즉시 제거하고 모델을 철회한다. 경로·시간표·장치가 바뀌면 다시 검증한다.

미리보기 ETA 응답은 방문 ID·예상 도착시각·측정시각·만료시각만 담고, GPS와 회차 식별자는 돌려주지 않는다. 보관된 분 단위 사건 1,102건은 연구 참고자료이며 이 공개 기준의 정답으로 쓰지 않는다.
