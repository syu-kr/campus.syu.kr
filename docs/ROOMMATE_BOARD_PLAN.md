# 삼육대 기숙사 룸메이트 게시판 최종 구현 계획

2026년 10월 4일 기준 최종본 v1.0이다. 학교 이메일 링크로 최초 인증하고 같은 브라우저에서 재방문하는 삼육대 기숙사 룸메이트 게시판을 구현한다. 진입 위치는 캠퍼스 메뉴이며 신고와 게시글은 기존 admin에서 관리한다. 이 문서는 제품 동작, 서버 계약, 구현 순서와 검증 완료 기준이다.

사용자가 확정한 요구사항과 이 계획에서 정한 구현 기본값을 구분한다. 30일 접속 유지와 아래 제한 수치는 첫 버전의 구현 기준으로 사용한다. 실제 Firebase 요금제와 인증 설정, 메일 수신은 구현 과정에서 확인할 환경 검증 항목이며 확인되지 않은 값을 확정 사실로 취급하지 않는다. 계획 완성과 기능 구현, 공개 출시는 별도로 판단한다.

## 사용자 확정 사항

| 항목 | 확정한 범위 |
| --- | --- |
| 대상 | 삼육대학교 기숙사 룸메이트 모집 |
| 가입 | 별도 회원가입 화면이나 비밀번호 설정 없이 이용 |
| 인증 | Firebase 기본 발송을 사용하는 학교 이메일 링크 로그인 |
| 재방문 | 접속 상태가 유지된 같은 브라우저에서 바로 진입 |
| 공개 범위 | 목록, 상세, 생활습관과 연락 링크 모두 인증한 사용자에게만 제공 |
| 연락 | 작성자가 등록한 카카오 오픈채팅으로 연결 |
| 진입 위치 | 캠퍼스 메뉴, `/campus/roommates` |
| 운영 | 기존 `/admin`에서 신고와 게시글을 통합 관리 |
| 테스트 | 외부 사전 테스터 없이 우리가 직접 기능과 접근 권한을 검증 |
| 테스트 학교 메일함 | 사용자가 보유한 학교 주소를 제공함. 첫 시험은 `400 OPERATION_NOT_ALLOWED`였으나 후속 설정 조회에서 이메일 링크 활성화를 확인했고, 실제 발송 HTTP 200·사용자 수신·PC 로그인·재방문·로그아웃 후 차단을 확인함 |
| 테스트 Firebase | 사용자가 별도 프로젝트를 아직 만들지 않았다고 확인. 운영 DB에 테스트 글을 넣지 않음 |
| 출시 시점 | 고정 마감일 없음 |

학생 이메일 인증은 이메일 소유 확인이다. 현재 재학 상태, 기숙사 합격이나 공식 방 배정을 보증하는 배지로 표현하지 않는다. 게시판에서 상대를 찾은 뒤 공식 입사 신청과 룸메이트 지정 절차는 학생이 해당 학기 학교 공지에 따라 진행한다.

## 구현 기본값

| 항목 | 기본값과 의미 |
| --- | --- |
| 접속 유지 | 최초 인증일부터 고정 30일. 방문이나 글 수정으로 연장하지 않음 |
| 유지 선택 | `이 브라우저에서 30일 유지` 기본 선택. 공용 기기에서는 해제하도록 안내 |
| 장기 유지 해제 | 서버 세션은 최대 12시간. 브라우저 종료만으로 로그아웃된다고 약속하지 않음 |
| 인증 링크 | Firebase가 발급과 유효성을 검증. 자체 숫자 코드나 5분 만료를 적용하지 않음 |
| 재발송 | 이메일당 60초 간격, 시간당 5회, 하루 10회 |
| 공용망 보조 제한 | IP당 시간당 100회. 개인별 제한과 별도로 적용 |
| 제공자 발송 한도 | Firebase 요금제에 따름. 로그인 링크는 Spark 5통/일, Blaze 25,000통/일 |
| 모집글 | 이메일당 활성 글 1개, 신규 등록 하루 최대 3회 |
| 모집 기간 | 한국 시간 기준 등록일 포함 최대 30일. 작성자는 그 안에서 모집 마감일을 선택 |
| 내용 수정 | 정렬 기준인 최초 등록 시각과 모집 마감일을 연장하지 않음 |
| 신고 | 인증 이메일당 한 글에 1회, 자기 글 신고 불가, 하루 최대 5건 |
| 작성 보류 | 관리자 숨김 시 기본 30일. 관리자 조기 해제와 30일 연장 가능. 기한 종료 후 신규 작성 허용 |
| 목록 | 최신순, 응답당 최대 20개, 서버가 요청당 최대 100개 후보 확인 |
| 조회 빈도 | 목록과 상세를 합쳐 작성자 키당 분당 30회, IP당 분당 120회. 필터나 글 ID 변경으로 초기화하지 않음 |

발송, 신규 등록과 신고의 앱 일일 제한은 UTC 날짜 경계, 시간당과 분당 제한은 서버의 고정 구간으로 계산한다. 앱 제한의 다음 이용 가능 시각은 한국 시간으로 표시한다. Firebase의 실제 한도 갱신 시각을 앱 계산과 같다고 가정하지 않고 제공자 제한 오류에서는 확인되지 않은 재개 시각을 단정하지 않는다.

30일 유지 중에도 서버는 요청마다 세션의 만료와 폐기 상태를 검사한다. 로그아웃, 쿠키 삭제, 새 브라우저, 유지 기간 만료 후에는 다시 이메일 링크 인증이 필요하다. 모바일 설치 앱과 카카오 인앱 브라우저의 인증 공유 여부는 실제 환경에서 확인한 결과대로 안내한다.

## 화면과 이용 흐름

진입 메뉴는 `캠퍼스 > 룸메이트 구하기`, 기본 경로는 `/campus/roommates`다. `app/campus/page.tsx`의 기존 메뉴 카드에 추가하고 기존 한국어와 영어 경로 정책을 따라 `/en/campus/roommates`에서도 같은 기능을 제공한다. 사용자 소개글은 작성 원문을 표시한다.

| 화면 | 경로 | 사용자 동작과 필수 상태 |
| --- | --- | --- |
| 이메일 인증 | `/campus/roommates/verify` | 이메일 입력, 인증 메일 받기, 링크 클릭 완료, 재전송, 접속 유지 선택, 학교 메일 발급 안내 |
| 링크 완료 | `/campus/roommates/verify/finish` | 링크 검증, 필요한 경우 수신 이메일 재입력, 서버 세션 발급 후 원래 화면 이동 |
| 모집 목록 | `/campus/roommates` | 기숙사와 인실, 기간과 생활습관 필터, 모집 카드, 더 보기, 내 글 관리 |
| 모집글 작성 | `/campus/roommates/new` | 기본 조건, 생활습관과 오픈채팅 입력, 등록 전 공개 항목 확인 |
| 모집글 상세 | `/campus/roommates/[postId]` | 생활습관 전체, 소개, 마감일, 오픈채팅 연결, 신고 |
| 내 글 관리 | `/campus/roommates/me` | 수정, 모집 완료, 삭제, 완료나 만료 후 다시 모집 |
| 관리자 룸메이트 관리 | 기존 `/admin`에 통합 | 신고와 글 조회, 숨김과 복구, 삭제, 작성 보류와 해제, 처리 기록 |

유효한 세션이 있으면 인증 화면을 거치지 않는다. 상세 링크에서 인증이 필요해졌다면 인증 성공 후 해당 상세로 돌아간다. 돌아갈 주소는 사이트 내부의 허용된 룸메이트 경로로만 제한한다.

빈 목록, 아직 남은 검색 후보, 로딩, 요청 제한, 만료된 세션, 모집 종료, 숨겨진 글과 서버 장애를 구분한다. 장애를 로그아웃이나 검색 결과 없음으로 표시하지 않는다. 모집 종료나 삭제 후 다른 사용자는 소개와 연락 링크를 열 수 없고 종료 안내만 받는다.

인증 화면은 모바일 이메일 키보드와 자동완성을 지원하고 메일의 링크를 열도록 안내한다. 폼의 각 항목에 레이블을 붙이고, 오류 필드로 초점을 이동한다. 신고와 삭제 확인 창은 기존 Modal 패턴을 재사용한다.

## 모집글 입력 규칙

| 항목 | 입력과 검증 |
| --- | --- |
| 닉네임 | 필수, 2자부터 12자. 실명 입력을 요구하지 않음 |
| 기숙사와 인실 | 필수, 공식 공지에서 확인한 조합만 선택 |
| 거주 시작일과 종료일 | 필수, 실제 달력 날짜 검증, 시작일이 종료일보다 늦을 수 없음 |
| 구하는 인원 | 필수, 1명부터 해당 인실 정원에서 본인 1명을 뺀 수까지 |
| 모집 마감일 | 필수, 기본 등록일 포함 30번째 날과 거주 종료일 중 빠른 날짜. 오늘부터 등록일 포함 30일 범위에서 선택 |
| 생활습관 | 선택 항목. 미선택은 `미기재`로 표시하고 `상관없음`과 구분 |
| 소개 | 선택, 최대 300자, 일반 텍스트 |
| 카카오 오픈채팅 | 필수, `https://open.kakao.com/o/{영문과 숫자로 된 코드}` 형식. 다른 호스트, 사용자 정보와 임의 포트 금지 |

거주 기간과 마감일은 한국 시간의 달력 날짜로 입력한다. 거주 종료일이 이미 지난 글은 새로 등록할 수 없다. 모집은 선택한 마감일의 다음 날 0시부터 종료하며, 마감일은 거주 종료일을 넘을 수 없다. 서버는 이 경계를 UTC Timestamp로 변환해 저장하고 요청마다 비교한다.

카드 제목은 기숙사, 인실과 모집 인원으로 생성한다. 예를 들어 `에덴관 3인실 룸메이트 1명 구해요`처럼 표시한다. 별도 제목 필드를 늘리지 않는다.

초기 기숙사 조합은 2026년 2학기 공식 공지를 기준으로 브니엘 2인실, 살렘 2인실, 시온 2인실과 3인실, 에덴 2인실과 3인실과 4인실이다. 1인실은 룸메이트 모집 대상에서 제외한다. 다음 모집 시즌에는 공식 공지를 다시 확인하고 설정을 갱신한다. 첨부 이미지에 있는 인실만으로 현행 조합을 확정하지 않는다. [2026년 2학기 생활교육원 입사 신청 안내](https://www.syu.ac.kr/dorm/2026-2-%EC%83%9D%ED%99%9C%EA%B5%90%EC%9C%A1%EC%9B%90-%EC%9E%85%EC%82%AC-%EC%8B%A0%EC%B2%AD-%EC%95%88%EB%82%B4/)

생활습관은 다음 여덟 항목과 선택값으로 구현한다. 취침, 기상, 청소, 통화, 흡연과 물건 공유는 단일 선택이다. 잠버릇과 냉난방은 복수 선택이며 잠버릇의 `없음`과 `잘 모름`은 다른 값과 동시에 선택할 수 없다.

| 항목 | 선택값 |
| --- | --- |
| 취침 | 22시 이전, 22시부터 24시, 0시부터 2시, 2시 이후, 유동적 |
| 기상 | 6시 이전, 6시부터 8시, 8시부터 10시, 10시 이후, 유동적 |
| 청소 | 자주, 정기적으로, 함께 협의 |
| 실내 통화 | 밖에서, 짧은 통화 가능, 함께 협의 |
| 잠버릇 | 없음, 코골이, 이갈이, 잠꼬대, 잘 모름. 복수 선택 허용 |
| 흡연 | 비흡연, 흡연. 기숙사 내 흡연 허용 여부를 의미하지 않음 |
| 냉난방 | 더위에 민감, 추위에 민감, 함께 협의. 민감 항목 복수 선택 허용 |
| 물건 공유 | 공유하지 않음, 허락 후 가능, 함께 협의 |

사진, 첨부파일, 댓글, 자체 채팅, AI 추천 점수, 학번과 생년 필드, 과거 글 아카이브는 첫 버전 범위에 넣지 않는다. 실명, 전화번호와 정확한 호실을 소개에 적지 않도록 작성 화면에서 안내한다. 입력 제한만으로 개인정보 노출이나 괴롭힘 신고가 모두 해결된다고 가정하지 않는다.

## 학생 이메일과 발송 서비스

2026년 1월 29일 정보전산팀의 공식 신편입생 안내 첨부 PDF 17쪽부터 20쪽에서 학생 이메일은 `@syuin.ac.kr`로 확인했다. SU-WINGs의 `학생 > 서비스 > 기타 > 오피스365`에서 재학 상태인 학생이 신규 계정을 만들고 Outlook 웹메일을 사용하는 경로가 안내되어 있다. 아이디는 학생이 정하므로 학번 형식을 강제하지 않는다. [2026학년도 신편입생 정보서비스 이용 안내](https://www.syu.ac.kr/blog/2026%ED%95%99%EB%85%84%EB%8F%84-%EC%8B%A0-%ED%8E%B8%EC%9E%85%EC%83%9D-%EC%A0%95%EB%B3%B4%EC%84%9C%EB%B9%84%EC%8A%A4-%EC%9D%B4%EC%9A%A9-%EC%95%88%EB%82%B4/)

운영 인증 허용 도메인은 정확히 `syuin.ac.kr` 하나다. 교직원 주소에 쓰이는 `syu.ac.kr`, 유사 도메인과 외부 메일은 허용하지 않는다. 이메일은 앞뒤 공백을 제거하고 소문자로 정규화한다. Gmail식 점 제거 같은 별도 별칭 합치기는 하지 않는다.

안내문은 재학생의 신규 발급 조건을 설명한다. 휴학이나 졸업 후 기존 계정이 언제 종료되는지는 이 확인으로 판단할 수 없다. 실제 인증 메일 1회 수신과 PC 링크 완료는 확인했다. 공개 전 전달 시간, 스팸 분류와 재발송도 확인한다. 메일 미발급 사용자는 공식 발급 안내를 제공하고, 인증 조건을 임의로 다른 메일로 완화하지 않는다.

Firebase Authentication의 기본 인증 메일은 Google이 발송하므로 별도 SMTP나 Resend 연결 없이 사용할 수 있다. 기본 템플릿은 정해진 인증 흐름에 사용하는 것이며 임의의 숫자 OTP 메일을 보내는 범용 발송기가 아니다. `sendEmailVerification`은 기존 Firebase 사용자의 주소 확인, `sendSignInLinkToEmail`은 비밀번호 없는 로그인 링크 발송에 쓰인다. 이 게시판에는 사용자가 선택한 후자를 적용한다. [인증 링크와 기본 발송 설명](https://firebase.google.com/docs/auth/admin/email-action-links), [이메일 로그인 가이드](https://firebase.google.com/docs/auth/web/email-link-auth)

주소 확인을 이용한 별도 로그인 설계가 기술적으로 불가능하다는 뜻은 아니다. 다만 과거의 `emailVerified=true`만 보고 현재 접속자의 소유를 판단할 수 없으므로 인증 요청과 링크, 일회성 사용과 세션 발급을 별도로 연결해야 한다. 첫 버전은 이 대안을 구현하지 않고 Firebase 이메일 링크 로그인을 사용한다.

2026년 10월 4일에 확인한 기본 발송의 공식 일일 한도는 아래와 같다. 표는 문서상 기준이며 현재 프로젝트의 실제 요금제, 인증 설정과 잔여량은 콘솔에서 확인하지 않았다.

| 기본 발송 종류 | Spark | Blaze |
| --- | ---: | ---: |
| 이메일 주소 확인 | 1,000통/일 | 100,000통/일 |
| 비밀번호 재설정 | 150통/일 | 10,000통/일 |
| 이메일 링크 로그인 | 5통/일 | 25,000통/일 |

Firebase는 링크 로그인 5통을 초과하려면 결제 수단을 추가해야 한다고 명시한다. 한도는 사용자 수에 따라 조정되며 남용 방지 제한이 추가될 수 있다. 로그인 링크 생성 한도는 Spark 20,000개/일, Blaze 250,000개/일로 발송과 별개다. Admin SDK의 `generateSignInWithEmailLink`는 링크를 생성할 뿐 메일을 직접 보내지 않으므로 생성 한도를 기본 발송 한도로 읽지 않는다. [Firebase Authentication 한도](https://firebase.google.com/docs/auth/limits)

Spark의 하루 5통은 소수의 실제 수신 시험에 쓸 수 있지만 공개 모집 게시판의 최초 인증에는 부족하다. Blaze라면 별도 발송 서비스를 추가하지 않고 기본 발송을 사용하는 방향이다. 실제 플랜을 확인한 뒤 공개 규모에 맞는 한도를 판단하며, 요금제 변경이나 결제 연결은 이 문서 작업에서 수행하지 않는다. 주소 확인 메일의 더 큰 한도를 로그인 링크의 한도로 대신 적용하지 않는다.

Firebase 기본 템플릿과 기본 발신 주소부터 사용한다. 별도 발신 도메인과 DNS 설정은 초기 필수 준비에서 제외한다. 콘솔의 Email/Password 제공자와 Email link 기능, 운영과 테스트 도메인, 한국어와 영어 템플릿을 확인한다. 개발용 localhost는 테스트 프로젝트에서만 필요에 맞게 허용하고 deprecated `dynamicLinkDomain`은 사용하지 않는다. 웹과 설치 웹앱의 HTTPS 완료 경로를 사용하며 네이티브 앱용 Dynamic Links 구성을 추가하지 않는다.

메일 요청은 사이트 서버에서 학생 도메인과 이메일별 재전송 제한을 확인한 뒤 Firebase 기본 발송 API로 보낸다. `accounts:sendOobCode`의 `EMAIL_SIGNIN` 흐름을 기존 `fetch`와 프로젝트의 웹 API 키로 호출한다. 서버가 허용한 한국어 또는 영어의 `/campus/roommates/verify/finish` 완료 URL과 `canHandleCodeInApp: true`를 정하며 브라우저의 임의 완료 URL을 받지 않는다. 메일 API를 Firestore 트랜잭션 안에서 호출하지 않고 요청 시간 초과에서도 자동 재호출로 중복 발송하지 않는다. 기본 API 호출 방식과 에러 변환은 분리된 테스트 프로젝트에서 검증한다. [공식 발송 REST API](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v1/accounts/sendOobCode)

Firebase 공개 인증 API에 대한 직접 요청까지 사이트의 제한으로 모두 통제했다고 주장하지 않는다. 학생 도메인은 서버의 게시판 접근 조건으로 검사하고 Firebase Auth 사용자 생성 자체와 구분한다. 초기 계획에는 Turnstile과 추가 발송 의존성을 넣지 않고 기본 제공자 보호와 앱 제한부터 사용한다. 실제 발송 남용이 나타나면 제공자 설정과 보호 수단을 별도로 검토한다.

발송 한도나 제공자 장애는 기존 유효 세션을 무효화하지 않는다. 발송 중지 중에도 이미 받은 유효 링크를 통한 완료와 로그아웃은 유지한다. 학교 메일함은 사용자가 보유하고 있어 준비 완료로 기록하며, 실제 메일의 도착 시간과 스팸 분류, 재발송을 시험한다. 학교 메일 비밀번호나 SU-WINGs 비밀번호를 사이트에서 받지 않는다.

## 서버 인증과 권한

기존 Next.js API, Firebase Web SDK와 Admin SDK, 서버 요청 제한과 입력 검증을 재사용한다. 새 인증 라이브러리나 DB를 추가하지 않는다. 학생용 클라이언트 인증은 같은 프로젝트의 이름 있는 secondary Firebase app으로 분리한다. 기존 `lib/firebase.ts`의 기본 app과 `auth`를 관리자와 FCM이 사용하므로 학생 로그인으로 덮어쓰지 않는다. 사용자 저장소는 같은 Firebase 프로젝트에 속하며 별도 프로젝트나 회원 프로필을 새로 만들지는 않는다.

1. 발송 요청은 이메일과 IP의 앱 제한을 서버의 공용 저장소에서 확인한다. 이메일 원문이나 인증 링크를 로그에 남기지 않는다. Firebase 발송 실패와 시간 초과를 성공처럼 안내하지 않는다.
2. 메일의 링크를 연 완료 화면에서 `isSignInWithEmailLink`와 `signInWithEmailLink`를 사용한다. 같은 브라우저에서는 발송 때 임시 보관한 이메일을 사용하고 다른 브라우저에서는 수신 이메일을 다시 입력받는다. 이메일을 완료 URL의 매개변수로 넘기지 않는다. 임시 주소는 성공이나 취소 때 제거하고 최대 24시간 후에는 사용하지 않는다.
3. 학생용 auth는 `inMemoryPersistence`로 두어 Firebase refresh token을 장기 보관하지 않는다. 클라이언트의 현재 사용자만으로 게시판 접근을 허용하지 않고 ID token을 서버 세션 발급 API에 보낸다. 완료 경로는 애플리케이션 로그, Sentry와 사이트 분석에서 민감한 링크 값이 수집되지 않도록 제외하거나 필터링하고 처리 후 주소에서 제거한다. 배포 환경의 요청 URL 기록 범위도 확인한다.
4. 서버는 Admin SDK의 `verifyIdToken(token, true)`로 ID token과 폐기 상태를 검증하고, 인증된 이메일과 `email_verified`, 정확한 학생 도메인, UID와 최근 로그인 시각을 확인한다. 발급 요청의 이메일, 작성자 키나 인증 완료 플래그를 신뢰하지 않는다. 세션 발급은 최근 5분 안의 `auth_time`에서만 허용한다.
5. 서버가 무작위 게시판 세션을 발급한다. 쿠키 이름은 `__Host-roommates_session`이며 `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`를 사용하고 Domain은 지정하지 않는다. Firestore에는 토큰의 SHA-256만 저장한다. 고정 만료 시각은 검증된 로그인 시각에서 30일 또는 12시간이며 방문이나 token 재전송으로 연장하지 않는다. 발급 성공 후 학생용 Firebase auth를 로그아웃한다.
6. 서버 페이지와 목록, 상세, 내 글과 모든 쓰기 API에서 게시판 세션을 검사한다. `getUser(uid)`로 삭제와 비활성화, 이메일 인증 상태와 정확한 도메인을 확인하고 현재 이메일의 HMAC이 세션의 작성자 키와 일치하는지 비교한다. 저장한 `auth_time`보다 `tokensValidAfterTime`이 뒤면 폐기된 세션으로 거부한다. ID token을 저장하지 않아도 Firebase의 사용자 변경과 폐기를 자체 세션에 반영한다. 인증 인프라 장애는 `503`으로 처리하고 정상적인 로그아웃으로 오인하지 않는다.
7. 로그아웃은 현재 게시판 서버 세션과 쿠키를 폐기하고 학생용 임시 인증 상태를 지운다. 기존 관리자 auth의 `signOut`을 호출하지 않는다.

Firebase 링크 로그인 성공 뒤 게시판 세션 발급이 실패하면 학생용 임시 auth를 유지하고 최근 인증 5분 안에서 세션 API만 재시도한다. 소비된 링크를 다시 로그인에 사용하지 않는다. 세션 발급 성공이나 명시적 취소 때만 임시 auth를 제거하며 5분이 지난 경우 새 인증 메일을 요청하도록 안내한다.

30일 유지에는 자체 세션 저장소를 사용한다. Firebase Admin의 `createSessionCookie`는 최대 2주까지만 지원하므로 첫 버전에서는 사용하지 않는다. Firebase 클라이언트의 자동 token 갱신으로 고정 30일 제한을 우회하는 설계도 사용하지 않는다. [Firebase 서버 쿠키 기간과 클라이언트 상태 처리](https://firebase.google.com/docs/auth/admin/manage-cookies)

`ownerKey`는 서버에서 검증한 정규화 이메일에 별도 비밀 키를 적용한 HMAC으로 계산한다. 같은 이메일을 다시 인증하면 같은 내부 작성자 키를 얻는다. Firestore의 모집글과 세션에 원문 이메일, Firebase ID token과 refresh token, 링크의 OOB code, 세션 토큰 원문을 저장하지 않는다. Firebase Auth에는 인증용 사용자 레코드와 이메일이 저장된다. 별도 회원가입 화면이 없다는 것과 인증용 사용자 자료가 없다는 것을 혼동하지 않고 개인정보 안내에 반영한다.

작성자 식별용 HMAC 키는 별도 운영 비밀값이며 OTP HMAC 키는 더 이상 필요하지 않다. 식별 키 교체는 기존 글과 작성자의 연결에 영향을 주므로 데이터 이전 또는 기존 글 만료와 연결해 다룬다.

기존 `enforceRateLimit`은 IP를 키에 붙이는 구조다. 이메일별 제한까지 IP별로 나뉘지 않도록 명시적인 서버 키를 받는 작은 공통 함수를 추가하고 `api_rate_limits`를 재사용한다. 세션 정리나 재배포로 제한 카운터가 초기화되어서는 안 된다.

학생용 발송, 세션 발급과 모든 쿠키 기반 쓰기 요청은 Origin을 필수로 받고 요청 대상 사이트와 정확히 같은 출처인지 검사한다. 누락, `null`과 불일치는 `403`으로 거부한다. 기존 다른 기능의 Origin 정책은 바꾸지 않는다. 돌아갈 URL은 허용된 캠퍼스 룸메이트 내부 경로만, 연락 URL은 정해진 카카오 형식만 서버에서 검증한다. 카카오 링크는 저장과 이동만 지원하고 서버가 미리 가져오지 않는다.

## 데이터와 API 계약

회원 프로필을 만들지 않고 인증, 모집글과 운영에 필요한 자료만 저장한다. 아래 네 컬렉션을 사용한다. `expires_at`은 물리 정리 시각이며 모집 마감인 `recruit_until`과 구분한다. Firestore 클라이언트 직접 접근 거부 정책은 유지하고 서버 Admin SDK로만 처리한다.

| 컬렉션 | 필요한 자료 |
| --- | --- |
| `roommate_sessions/{tokenHash}` | 작성자 키, 검증된 Firebase UID와 로그인 시각, 생성 시각, 고정 만료 시각 |
| `roommate_posts/{randomPostId}` | 내부 작성자 키, 닉네임, 모집 조건, 생활습관, 소개, 연락 링크, 상태, version, 등록과 수정 시각, 모집 마감과 정리 시각 |
| `roommate_owner_state/{ownerKey}` | 활성 글 ID, 최신 글 ID, 작성 보류 만료 시각 `hold_until`, 보류 사유, 갱신과 정리 시각. 첫 글 작성 때만 생성 |
| `roommate_reports/{reportKey}` | 글 ID, 신고자 내부 키, 사유와 당시 최소 근거, 처리 상태와 version, 접수와 처리 시각, 정리 시각 |

Firebase가 로그인 링크를 관리하므로 OTP challenge 컬렉션은 만들지 않는다. 작성자 상태 문서는 동시 등록에서도 활성 글 한 개를 지키고 숨김 이후 삭제와 재등록으로 작성 제한을 초기화하지 않기 위해 둔다. 사용자 프로필로 사용하지 않는다. 신고는 별도 문서로 두어 글 삭제 후에도 동일한 글에 대한 처리 대상을 유지한다.

| API | 인증과 처리 |
| --- | --- |
| `POST /api/roommates/auth/request-link` | 학생 이메일과 앱 제한 검증, Firebase 기본 발송. 링크와 OOB code 반환 금지 |
| `POST /api/roommates/auth/session` | Firebase ID token과 최근 인증, 학생 도메인, 유지 선택 검증. 게시판 세션 쿠키 발급 |
| `GET /api/roommates/auth/session` | 최소 인증 상태 반환. 원문 이메일과 서버 토큰 반환 금지 |
| `POST /api/roommates/auth/logout` | 현재 세션 폐기, 쿠키 제거 |
| `GET /api/roommates/posts` | 인증 필수. 필터와 cursor 기반 목록 |
| `POST /api/roommates/posts` | 인증 필수. 작성자 상태와 글을 트랜잭션으로 생성 |
| `GET /api/roommates/posts/me` | 인증 필수. 본인의 최신 글과 관리 가능 상태 |
| `GET /api/roommates/posts/[postId]` | 인증 필수. 노출 가능한 상세만 반환 |
| `PATCH /api/roommates/posts/[postId]` | 작성자만 내용 수정 또는 모집 완료. version 확인 |
| `DELETE /api/roommates/posts/[postId]` | 작성자만 삭제. 공개 조회와 연락은 즉시 차단 |
| `POST /api/roommates/posts/[postId]/reports` | 인증 필수. 서버가 신고자 키 결정, 중복과 자기 글 신고 차단 |
| `GET`과 `PATCH /api/admin/roommate-reports` | 기존 `requireAdmin`으로 신고 확인과 처리, 감사 기록 |
| `GET`과 `PATCH /api/admin/roommate-posts` | 기존 `requireAdmin`으로 신고 없는 글도 조회, 숨김과 복구, 삭제, 작성 보류와 해제. version 확인 |

동시 요청에 대한 규칙은 다음과 같다.

- 글 등록과 내용 수정 트랜잭션은 작성자 상태의 `hold_until`을 검사한다. 현재 시각보다 뒤면 `403`으로 거부한다. 보류 중에도 본인 삭제와 모집 완료는 허용한다.
- 글 등록은 작성자 상태와 현재 활성 글을 함께 확인한다. 두 등록 요청 중 하나만 성공하고 다른 요청은 `409`를 받는다. 포인터 대상이 없거나 모집 중인 유효 글이 아니면 같은 트랜잭션에서 포인터를 정리한다. 숨김 글은 보류 종료 후 신규 작성이 가능해져도 자동 복구하지 않는다.
- 글은 version 1부터 시작한다. 사용자 PATCH와 DELETE는 JSON 본문의 `expectedVersion`을 필수로 받고 대상 글의 작성자와 version을 검사한다. 불일치는 `409`다. 늦게 도착한 수정은 이미 완료되거나 삭제된 글을 다시 열지 못한다.
- PATCH의 action은 `update` 또는 `complete`이며 등록과 수정에 허용된 입력 필드만 받는다. 작성자 키, 등록 시각, 마감일 연장이나 직접 status 지정은 거부한다. 완료와 삭제는 재호출로 상태나 보존 기한이 연장되지 않게 처리한다.
- 완료와 삭제는 활성 포인터가 해당 글을 가리킬 때만 해제한다. 이전 글에 대한 늦은 요청이 새 모집글의 포인터를 지우지 못한다.
- 숨긴 글을 삭제하거나 재인증해도 `hold_until`은 유지한다. 관리자 해제 또는 지정된 기한 종료만으로 신규 작성이 가능해진다.
- 관리자 숨김은 글의 version 확인, `hidden` 전환, 활성 포인터 해제와 작성 보류 설정을 같은 트랜잭션으로 처리한다. 새 보류의 기본 기한은 조치 시점부터 30일이며 기존 기한을 단축하지 않는다. 명시적 연장은 현재 보류 기한과 현재 시각 중 늦은 시각에 30일을 더한다.
- 복구는 `hidden → recruiting`만 허용한다. version, 마감일과 활성 포인터를 확인하며 다른 활성 글이 있거나 마감이 지났으면 복구하지 않는다. `completed`와 `deleted` 글은 복구하지 않는다. 글 복구와 작성 보류 해제는 별도 조치로 표시한다.
- `status`는 `recruiting`, `completed`, `hidden`, `deleted`다. 화면의 만료 상태는 서버 현재 시각과 `recruit_until`로 계산한다.
- 모집 중인 글만 상세와 연락을 일반 사용자에게 제공한다. 본인과 관리자에게 필요한 관리 상태는 별도 응답으로 제공한다.

신고 사유는 스팸, 허위 정보, 부적절한 내용, 개인정보 노출과 기타다. 설명은 선택이며 최대 300자다. 서버가 글 ID와 신고자의 `ownerKey`로 결정적인 reportKey를 계산하고, 글의 현재 모집 상태 확인, 중복 확인과 당시 근거 복사를 한 트랜잭션에서 처리한다. 동시 신고에서도 한 건만 생성한다. 신고 자체로 글 상태나 작성 보류를 바꾸지 않는다.

신고 처리 상태는 `pending`, `reviewing`, `done`, `rejected`다. 글의 모집 상태와 구분한다. 관리자 신고 PATCH는 report ID, expectedVersion, 처리 상태와 최대 300자의 처리 메모만 받는다. 글 숨김과 삭제는 글 관리 API에서 수행하고, 글 조치와 신고 처리를 각각 기록한다. 상태와 version 확인은 서버 트랜잭션으로 처리한다.

공통 오류는 입력 `400`, 미인증이나 만료 `401`, 권한과 보류 `403`, 일반 사용자에게 노출할 수 없는 글 `404`, version과 활성 글 충돌 `409`, 요청 제한 `429`, 설정과 제공자 장애 `503`으로 구분한다. 보호 API는 인증부터 확인한다. `404`에서 소개와 연락을 반환하지 않고 `종료되었거나 볼 수 없는 글`로 안내한다.

일반 응답은 작성자 내부 키, 인증 자료와 신고자 정보를 포함하지 않는다. 목록은 요약 필드와 생활습관 태그만, 상세는 소개와 연락 링크까지 반환한다. 공개 post ID는 이메일에 기반하지 않은 무작위 ID다.

기숙사, 인실, 거주 날짜 겹침과 생활습관을 서버에서 필터링한다. 선택한 생활습관 조건은 모두 일치해야 하는 AND 조건이다. 복수 선택 값은 글에 해당 값이 모두 들어 있어야 일치한다. 미기재 값은 특정 습관의 일치 결과로 취급하지 않는다. 조건을 바꾸면 cursor를 초기화하고 검색 조건은 URL에 유지한다.

초기 목록은 `recruiting` 글의 등록 시각 내림차순과 문서 ID 순서로 읽는 복합 인덱스를 둔다. 서버는 최대 100개를 확인하며 만료와 필터를 적용해 최대 20개를 반환한다. 결과 수를 채우거나 확인 한도에 도달하면 마지막으로 확인한 문서의 정확한 Timestamp와 ID를 cursor에 담는다. 마지막 일치 결과로 cursor를 잡아 중복 읽기나 누락을 만들지 않는다.

응답은 `{ items, nextCursor }`를 기준으로 한다. `items`가 비어 있어도 `nextCursor`가 있으면 아직 검색이 끝난 것이 아니다. 화면은 남은 후보 검색 상태와 `계속 찾기`를 제공하며, cursor가 없어졌을 때만 최종 검색 결과 없음으로 표시한다. 조회 한 번으로 전체 건수를 계산하거나 전체 컬렉션을 브라우저로 내려보내지 않는다. 선택도가 높은 필터의 실제 지연과 읽기 비용이 문제가 되면 해당 필터의 DB 인덱스부터 추가한다.

## 캐시와 데이터 보존

한국어와 영어의 게시판 페이지, 인증과 모집글 API, 새 관리자 룸메이트 API에 `private, no-store`를 적용한다. 게시글 metadata와 HTML, RSC에 미인증 사용자에게 제공할 내용을 넣지 않는다. 게시판을 sitemap과 공개 검색 인덱스에 등록하지 않고 `noindex`를 사용한다. 접근 차단의 근거는 검색 설정이 아니라 서버 인증이다.

React Query의 게시판 데이터는 사용자 전환, 로그아웃과 `401` 응답에서 요청을 취소하고 제거한다. 폼, 상세와 연락 링크도 함께 지운다. 다른 탭에는 개인정보 없는 세션 변경 신호를 보내고, 탭 복귀 시 서버 인증 상태를 다시 확인한다. 브라우저 뒤로가기와 페이지 복원에서도 세션 확인 전 이전 내용을 보여주지 않도록 테스트한다. 만료 시각에는 화면도 인증 상태를 갱신한다.

전체 기능 중지의 `503 FEATURE_DISABLED`에서도 이전 게시판 데이터를 제거하고 중지 안내를 표시한다. 일반 서버 장애의 `503`과 구분해 장애 때문에 사용자 세션을 폐기하지 않는다.

보존 규칙은 다음과 같다. 구현 시 개인정보 안내에 동일한 내용을 반영한다.

| 자료 | 접근 종료와 정리 |
| --- | --- |
| 인증 대기 이메일 | 브라우저에서 완료나 취소 시 제거. 최대 24시간 후 사용하지 않고 오래된 값을 정리 |
| 세션 | 만료 즉시 모든 보호 API에서 거부. 로그아웃은 즉시 삭제 |
| 완료와 삭제와 만료 및 숨김 글 | 일반 조회와 연락 즉시 차단. 최초 완료 또는 삭제 시각과 원래 모집 마감 시각 중 이른 시각에서 30일 후 정리. 숨김과 수정은 이 기한을 연장하지 않음 |
| 신고 기록 | 접수 후 기본 30일 보존. 보존 종료를 신고 해결로 표시하지 않음 |
| 비활성 작성자 상태 | 활성 글이나 작성 보류가 없는 상태에서 최종 활동 후 90일에 정리 |
| 작성 보류 상태 | 기본 30일의 `hold_until`로 관리. 유효 보류 중에는 상태 문서를 정리하지 않음. 기한 종료는 새 글 작성 허용이며 숨김 글 복구와 별개 |
| Firebase Auth 사용자 자료 | 삭제 요청 시까지 인증용 자료로 유지. 삭제 요청은 기존 사이트 문의에서 확인 후 처리하며 공유된 관리자와 다른 기능 계정을 무차별 삭제하지 않음 |
| 관리자 및 정리 감사 기록 | 기존 `admin_audit_logs`의 조치 후 365일 정리 규칙 사용. 신고 본문과 연락 링크를 중복 보존하지 않음 |

신규 신고는 인증 사용자가 모집 중인 글에만 접수한다. 접수된 신고는 글 종료 후에도 처리한다. 접수 때 관리자 전용 신고 문서에 당시 닉네임, 소개와 연락 링크 등 처리에 필요한 최소 근거를 복사하고 접수 후 30일에 함께 정리한다. 원문 글이 먼저 정리되어도 접수 시점의 근거는 해당 30일 동안 남지만 공개 응답으로는 반환하지 않는다. 연락 후 종료된 글에 대한 문제와 개인정보 삭제 요청, 이의제기는 기존 사이트 문의로 연결한다.

미처리 신고도 보존 기한에 도달하면 본문과 근거를 정리한다. 정리 직전 최소 식별자와 `미처리 상태에서 보존 종료`를 감사 기록에 남기고 관리자 조치로 처리 완료했다고 표시하지 않는다. admin은 접수일과 정리 예정일, 미처리 건수를 표시하고 신고가 남아 있으면 먼저 확인할 수 있게 한다.

실제 삭제 작업이 늦어져도 모든 읽기 API에서 상태와 만료를 검사한다. 기존 예약 정리 스크립트의 초기화와 배치 크기 패턴을 재사용하되 owner key로 반복 사용하는 작성자 상태를 과거 조회 결과만 보고 일괄 삭제하지 않는다. 삭제 직전에 트랜잭션으로 현재 만료 시각과 상태를 확인한다. 작성자 상태는 유효한 활성 글과 보류가 없고 최종 활동 후 90일이 지났을 때만 삭제한다. 부모 삭제로 하위 데이터가 자동 정리된다고 가정하지 않는다.

`/posts/me`는 최신 글이 정리되어도 남아 있는 작성 보류와 만료 시각을 함께 반환해 제한 사유를 안내한다. 글 포인터가 없으면 글 영역만 빈 상태로 표시한다. 기존 일일 정리 작업에 대상 컬렉션을 추가하며 Firestore 정리에서 Firebase Auth 계정을 자동 삭제하지 않는다.

## 운영과 공개 조건

정상 글의 사전 승인은 두지 않는다. 발송과 작성 제한, URL과 입력 검증, 만료와 모집 완료는 자동 처리한다. 신고 접수는 기록하고 관리자 신고함에 표시한다.

신고 수만으로 글을 자동 숨기거나 영구삭제하지 않는다. 신고 내용은 기존 admin에서 판단하고 관리자가 숨기는 경우 글 노출을 차단하며 작성자에게 사유, 보류 종료 시각과 기존 문의를 통한 이의제기 경로를 안내한다. 신고자 신원은 작성자에게 공개하지 않는다.

기존 `/admin`에 `룸메이트 관리` 영역을 추가해 현재 글과 신고를 함께 관리한다. 관리자 로그인, Bearer token, `requireAdmin`, 필터와 처리 상태, 감사 기록 패턴을 재사용한다. 기존 문의와 제보의 처리 흐름 및 AI 분류는 유지하고 같은 admin 안에서 관련 글과 신고를 연결한다. 별도 운영자를 새로 확보해야 한다는 조건은 두지 않는다. admin을 열면 미처리 신고와 정리 예정일을 먼저 확인하도록 배치한다. 첫 버전은 외부 알림 서비스를 추가하지 않으며 상시 대응 시간을 약속하지 않는다.

학생 이메일 인증만으로 관리자 자료나 처리 API에 접근할 수 없다. 학생 서버 세션과 관리자 Bearer token을 구분하며 `ADMIN_EMAILS` 권한 검사를 유지한다. 관리자 조치에는 실행자, 대상, 조치와 시각을 기록하되 신고 본문과 연락 링크를 감사 로그에 중복 복사하지 않아 신고 근거의 보존 기간을 우회하지 않는다.

제어는 전체 기능 중지, 글 쓰기 중지와 인증 메일 발송 중지를 구분한다. `ROOMMATES_ENABLED`가 꺼져 있으면 메뉴 표시뿐 아니라 페이지 직접 접근, 목록과 상세 API, 사이트의 링크 발송과 게시판 세션 발급을 서버에서 차단한다. 이때도 로그아웃과 관리자 사고 대응은 가능하게 한다. `ROOMMATES_WRITES_ENABLED`가 꺼져 있으면 신규 등록과 내용 수정만 중지하고, 조회와 본인 삭제, 모집 완료, 신고와 로그아웃은 유지한다. 글 쓰기 중지만으로 재인증을 막지 않는다. 사이트의 발송은 앱 제한과 별도 `ROOMMATES_EMAIL_ENABLED` 값에 따르며, 이미 받은 유효 링크의 완료와 세션 발급은 전체 기능 중지가 아닌 한 유지한다. 이 발송 플래그가 Firebase 공개 인증 API의 직접 호출까지 전역 차단한다고 표현하지 않는다. 전체 중지나 발송 중지로 재인증할 수 없어 본인 삭제가 불가능한 경우 외부 데이터 처리 문의 경로를 안내한다. 기존 다른 사이트 기능과 관리자 Auth 제공자를 끄지 않는다.

세 제어 값은 환경 설정으로 관리하고 변경 후 재배포로 적용한다. 첫 버전 admin에는 환경값을 수정하는 버튼을 만들지 않는다. admin의 즉시 조치는 글 숨김과 삭제, 보류와 해제, 신고 처리다.

운영 화면에는 미처리 신고, 현재 모집글과 앱에서 요청한 인증 메일 사용량을 보여준다. Firebase 전체 발송량이나 남은 제공자 한도를 앱 카운터만으로 확인했다고 표시하지 않는다. 자동화는 신고 판단을 대신하지 않는다. 카카오에서 이루어진 대화를 사이트가 읽거나 보관하지 않는다. 신고 범위는 게시글 내용과 링크, 사이트 이용 중 발생한 문제로 안내한다.

## 구현 순서와 완료 기준

| 단계 | 구체적인 작업 | 완료 기준 |

| 1 | 학생용 Firebase auth, 이메일 링크 완료, 앱 제한, 자체 쿠키 세션과 로그아웃 | 최초 인증과 재방문, 링크 오류, 세션 만료와 관리자 상태 분리 테스트 통과 |

실제 Firebase 설정 확인 전에도 1단계부터 3단계의 자동 테스트는 제공자 API와 token 검증의 모의 응답으로 검증할 수 있다. Auth Emulator가 출력한 링크는 상태 흐름 시험에 쓰되 실제 메일 수신 증거로 취급하지 않는다. 실제 수신 검증은 생략할 수 없으며 테스트 코드의 대체값을 운영 인증 경로에 넣지 않는다.

변경 위치는 아래 범위로 제한한다. 실제 파일 분리는 기존 패턴을 재사용하며 가장 작은 형태로 정한다.

- `app/campus/roommates/`, `app/features/roommates/`, `app/campus/page.tsx`: 서버 진입 확인과 화면, 캠퍼스 메뉴 카드.
- `app/api/roommates/`, `app/api/admin/roommate-reports/`, `app/api/admin/roommate-posts/`: 인증과 모집, 신고와 관리자 글 처리 API.
- `lib/roommates.ts`, `types/roommates.ts`, `lib/server/roommate-auth.ts`, `lib/server/roommate-posts.ts`: 선택값, 검증, 서버 인증과 트랜잭션.
- 학생용 Firebase 클라이언트 초기화: 기존 관리자와 FCM의 기본 app을 유지한 secondary app과 임시 인증 상태.
- `lib/i18n/roommates.ts`와 기존 `campus.menus` 사전 연결: 한국어와 영어 UI.
- `lib/server/http.ts`: 기존 동작을 유지하는 명시적 키 제한 기능.
- `next.config.js`, `firestore.indexes.json`, `scripts/cleanup_meet_rooms.ts`: 캐시, 인덱스와 정리 대상.
- `.env.example`, `docs/ENVIRONMENT_REGISTRATION.md`, `docs/FIRESTORE_RULES.md`, `app/privacy/page.tsx`, `app/terms/page.tsx`: 환경과 새 처리 항목 안내.
- `app/admin/page.tsx`와 관련 상세 영역: 기존 관리자 인증을 유지한 신고와 게시글 통합 관리.

새 환경 값은 아래 네 가지다. 기존 Firebase 클라이언트 설정, Admin 설정과 `RATE_LIMIT_SECRET`은 재사용한다. Resend API 키, 별도 발신 주소와 OTP HMAC 키, Turnstile 키는 요구하지 않는다.

| 환경 값 | 설정 기준 |
| --- | --- |
| `ROOMMATES_OWNER_KEY_SECRET` | 환경별 독립적인 무작위 HMAC 비밀값. 미설정 시 인증과 게시판을 `503`으로 거부 |
| `ROOMMATES_ENABLED` | 미설정 기본 false. 내부 검증 환경부터 true로 설정하고 공개 조건 충족 후 운영에서 활성화 |
| `ROOMMATES_WRITES_ENABLED` | 미설정 기본 false. 작성 검증 시 명시적으로 true |
| `ROOMMATES_EMAIL_ENABLED` | 미설정 기본 false. 해당 환경의 제공자와 수신 시험 조건 확인 후 true |

구현 전 설치된 `node_modules/next/dist/docs/`의 인증, cookies와 Route Handlers 가이드를 읽는다. 서버의 `cookies()`는 비동기로 읽고 쿠키 발급과 제거는 Route Handler에서 수행한다. 운영 비밀값을 Preview에 복사하지 않고 공유 문서에는 값 대신 변수 이름과 설정 위치만 기록한다.

저장소가 지정한 npm을 사용한다. 구현 후 관련 Vitest 테스트, `npm run type-check`, `npm run check:i18n`, lint와 build를 실행하고, 최종 단계에서는 CONTRIBUTING 문서의 `npm run check`를 통과시킨다. 실행하지 않은 테스트는 성공으로 기록하지 않는다. 이미 존재하는 다른 작업의 변경을 섞지 않는다.

테스트 결과에는 실행 환경, 명령, 실제 결과, UI 캡처와 검증하지 못한 항목을 남긴다. 내부 테스트로 사용성이나 실제 수요가 입증됐다고 판단하지 않는다. 공개 후에는 활성 모집글, 등록과 모집 완료의 추이, 인증 실패와 발송 한도 사용량으로 수요와 운영 부담을 확인한다. 지속적인 완료율이 필요해지면 식별 정보 없는 일별 집계를 별도 범위로 추가한다.
