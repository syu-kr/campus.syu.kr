# 디자인·사용성·로딩 성능 점검

이 문서는 2026-10-18~20의 조사·실험 이력이다. 아래의 ‘현재’·‘남은’은 각 기록 당시를 뜻한다. 현행 M3 UI 기준은 [UI 가이드](UI_DESIGN_GUIDE.md), 출시 보완과 새 검증은 [배포 준비 보고서](PRODUCTION_READINESS_2026-10-26.md)를 기준으로 한다. 과거 수치와 실패·원복 근거는 재현을 위해 보존한다.

2026-10-18 최초 조사, 2026-10-20 로컬 후속 검증·수정 결과 반영. 버튼·로고 디자인과 초기 로딩 문의에서 시작한 조사 및 수정 결과를 현행 상태 중심으로 정리했습니다. 최초 운영 화면 관찰, 코드 분석, 이후 로컬 production 비교를 구분합니다. 문서 정리 과정에서 과거 수치를 새로 측정한 것처럼 갱신하지 않았습니다.

불편을 설명하는 근거는 조작 요소와 정적 카드의 불명확한 구분, 작은 조작 영역·문자, 핵심 메뉴까지 긴 이동, 축소 시 로고 식별성, 화면별 표현 차이입니다. 입력 소실은 기능 문제이며 로고의 미적 선호는 사용자 시안 비교가 필요한 가설입니다.

## 시간표 성능 비교 기록

아래 시간표 표는 **기존 작업에서 실행한 로컬 측정**입니다. 메뉴·문서 정리 당시 재수집하지 않았으며, 이후 홈 캐시 측정은 별도 절에 기록합니다. 단계마다 대조군·SDK 조건이 다르므로 누적 개선율을 계산하지 않습니다. 재측정은 [성능 가이드](../PERFORMANCE.md)를 따릅니다.

### 공통 다국어 JS·Sentry 단계의 조건

Next.js 16.4.1 Turbopack production build/start, 같은 Windows 호스트, Chromium 155.0.8059.80, 390×844. 다운로드 200,000B/s·업로드 93,750B/s·추가 latency 0ms·CPU slowdown 4. 매 회 새 context의 빈 HTTP 캐시를 사용하되 HTTP/preload 재사용은 허용하고 서비스워커는 차단했습니다. 브라우저 interception 대신 로컬 압축 프록시를 사용했습니다.

전·후 모두 로컬 가짜 DSN으로 **실제 Sentry SDK 활성화**, 외부 ingest 없음. 배치 전 API와 해당 언어 SSR 각 1회 warmup, 측정 중 build/test/profile 정지. 강의 1,526개·JSON 696,996B·gzip level 6의 55,596B, SHA-256 `4ab295f3ec37dc65a944caecebe56d88ff1956466dd59a1052ad5dbec54c4d30`이 네 배치에서 일치했습니다. KO/EN 각각 전 5회·후 5회, 느린 회차도 포함합니다.

버튼 준비는 보이는 버튼에 React click handler가 연결된 첫 rAF입니다. 클릭 반응은 trusted pointerdown부터 모달 첫 article box를 감지한 rAF까지입니다. 진입→첫 결과에는 자동화 클릭 왕복 대기도 들어갑니다. SDK 보호는 global error/rejection handler의 SDK 표식이 처음 관측된 프레임이며 init 소요 시간과 다릅니다. 픽셀 표시 완료·INP·실기기 P95는 아닙니다.

## 대용량 JSON 캐시·홈 초기 로딩 조사와 최종 수정 — 2026-10-18

### 원인과 적용 범위

설치된 Next.js 16.4.1의 `patch-fetch.js`는 fetch 응답 본문을 모두 읽어 Base64로 직렬화합니다. `incremental-cache/index.js`는 이 항목의 `JSON.stringify(data).length`가 2MiB를 넘으면 production에서 경고를 내고 저장하지 않습니다. 기존 버전 JSON 요청은 모두 `force-cache`여서 저장할 수 없는 큰 응답에도 이 과정을 반복했습니다. 경고를 숨기거나 원본 크기 제한을 올려 해결할 수 있는 문제가 아닙니다.

고정한 공개 데이터에서 학사 공지는 원본 **1,673,940B**, AI metadata는 **5,391,760B**였습니다. 전자의 원본은 2MiB보다 작지만 각각 **2,232,304B·7,189,403B**의 직렬화 항목이 되어 저장에 실패했습니다. 앞선 운영 응답 관찰과 replay의 수치 차이는 응답 metadata도 직렬화하기 때문이며 두 기록을 JSON 원본 크기로 해석하지 않습니다.

- [crawl-data](../lib/server/crawl-data.ts)는 검증된 manifest의 raw `entry.size`가 **1MiB 초과**이면 `no-store`, 이하면 기존 `force-cache`를 사용합니다. Base64 증가분·metadata 여유를 둔 보수적 정책입니다. manifest 자체의 `no-store`와 60초 메모리 캐시, 버전별 최대 24개 Promise 캐시·동시 요청 공유, timeout·크기·SHA-256·구조 검증·출처 상태·번들 fallback·실패 후 재시도는 유지합니다.
- [홈](../app/page.tsx)·[본문](../app/features/home/HomePageClient.tsx)·스켈레톤은 조사 시작 당시 구조로 복원했습니다. 한국어와 영어 모두 검색·메뉴가 기존 7개 데이터 경계를 공유합니다. 이전 사용자 요청의 6개 메뉴 구성·순서는 유지하며, 직접 `?search` 진입도 기존 검색 화면을 사용합니다. 조기 표시 UI 시안은 최종 적용 범위에서 제외했습니다.
- 공용 [SearchBar](../app/components/SearchBar.tsx)는 hydration 전 입력과 첫 effect 직전 입력을 보존합니다. DOM 값을 React state로 채택하되 이미 큐된 입력 갱신을 우선하며, 초기 DOM 값이 기본값과 같으면 불필요한 setState 호출을 생략합니다. 검색 버튼 활성화·제출·초기화·자동 검색 부모 조건과 실제 `defaultValue` 변경은 계속 동기화합니다.

### 결과 해석과 남은 비용

- 모바일 server warm의 LCP 중앙값은 **1,780→1,416ms, 20.4% 단축**됐습니다. 검색 handler 준비 대리지표도 **4,423→4,198ms, 5.1% 단축**됐지만 여전히 약 4.2초입니다. 해당 두 지표는 이 5회 표본에서 전후 범위도 겹치지 않았습니다.
- 같은 조건의 FCP는 **1,172→1,416ms로 244ms 늦어졌습니다.** warm 경로에서 먼저 스켈레톤을 표시하는 대신 준비된 본문을 직접 반환하면서 첫 콘텐츠와 주요 본문을 함께 표시하는 교환관계가 있습니다. 모든 표시 지표가 좋아진 변경으로 설명하지 않습니다. TTFB 중앙값도 **28→39.7ms**로 늘었습니다.
- 모바일 server cold의 검색 handler 준비 대리지표는 **4,472.9→4,469.2ms**로 같은 수준입니다. LCP는 **2,768→2,688ms**였지만 전후 범위가 겹쳐 안정적인 개선을 입증하지 못했습니다. 빠르거나 느린 한 회차를 제외하지 않았습니다.
- 데스크톱 server warm의 LCP 중앙값은 **704→352ms**였지만 FCP는 **300→352ms**, 검색 handler 준비는 **771.8→798ms로 26.2ms 늦어졌습니다.** 준비 시간의 범위도 겹칩니다. 데스크톱의 조작 준비 개선으로 해석하지 않습니다.
- 홈 SSR reveal 스크립트 관측은 모바일 warm·데스크톱 warm 각각 전 **5/5 true → 후 5/5 false**, 모바일 cold는 전후 모두 **5/5 true**였습니다. 직접 반환 경로가 warm fallback 교체를 피한 관측과 일치합니다. 브라우저 CPU·hydration 비용 전체를 제거했다는 증거는 아닙니다.

최종 30방문의 폰트는 모두 **13요청·330,652B**, first-party JS는 모두 **16요청·322,426B**로 같았습니다. cold Pages upstream도 전후 모두 **8요청·gzip 1,486,500B**였고 같은 프로세스의 warm 방문에서 추가 요청은 **0건·0B**였습니다. warm 기록의 upstream 누적 카운터와 그 방문의 추가 요청량을 구분합니다. 이번 효과를 폰트·JS·원본 JSON 다운로드 총량 감소로 설명하지 않습니다.

공통 JS 실행과 hydration·CPU 스케줄링 비용은 남습니다. 5회 표본과 로컬 호스트 상태만으로 통계적 유의성·실사용자 p75/P95·실기기 성능을 확정하지 않습니다. 날짜를 고정한 주말 안내의 LCP 결과를 평일 식단·셔틀 상태나 다른 viewport의 LCP 요소로 일반화하지 않습니다.

### 이 배치에서 확인한 기능과 검증 한계

[홈 경로 단위 회귀](../app/page.test.tsx) **6개가 통과**했습니다. 최초 cold의 동기 경계·타이머 미생성, 7개 조회 완료 후 전환, 최초 실패 후 경계 유지, 빠른 warm의 동일 props·타이머 정리, 20ms 후 같은 Promise 스트리밍, 빠른·늦은 오류 전파를 검증합니다. 앞선 cache-only 절의 전체 검사 수치를 이번 렌더링 변경의 전체 회귀 검증으로 대신하지 않습니다.

helper 추출을 포함한 소스에서 전체 단위 테스트 **144개 파일·1,208개 테스트가 통과**했습니다(59.39초). 집중 홈 회귀 6개, 타입 검사와 변경한 2개 파일의 ESLint, 전체 lint와 다국어 검사도 통과했습니다.

최종 로컬 릴리스는 기존 `.env.local`의 DSN 설정을 유지하고 테스트 DSN으로 덮어쓰지 않은 상태에서 빌드했습니다. 업로드 토큰만 비워 실행한 `npm run build`는 **61/61** 생성으로 성공했고 BUILD_ID는 **`UdVLG1VR7wou4YbcGU9fB`**입니다. 생성된 `next-env.d.ts`를 기존 bytes로 복원한 뒤 최종 `npm run type-check`도 종료 코드 0이었습니다. 이 빌드는 helper 추출 후의 릴리스이며 앞선 가짜 DSN 계측 빌드와 구분합니다. 릴리스 빌드를 새로 실행했다는 사실로 위 성능 표를 다시 측정한 것처럼 바꾸지 않습니다.

이 릴리스에서 KO/EN 각각 320·390·1440px의 **6개 조건**을 실제 브라우저로 확인했습니다. 메뉴 순서·href·영어 경로 prefix, 필터 `aria-pressed`, 검색어 삭제·Enter 제출·결과 query·초기화·뒤로가기 복원과 도서관 이동 후 복귀가 통과했습니다. 메뉴의 관측 최소 크기는 **85.3×92px**였고 가로 넘침·page error·console error는 6개 조건 모두 0개였습니다.

처음 두 자동화 실행은 검색어 삭제 직후 바로 다시 입력하는 과정에서 query가 빈 값이고 제출 버튼이 disabled인 상태로 남아 URL 변경 대기 30초가 실패했습니다. 이후 삭제 후 disabled, 재입력 후 enabled를 각각 확인하는 상태 대기를 사용해 6개 조건을 완료했습니다. 이 과정에서 제품 소스는 바꾸지 않았습니다. 삭제·재입력이 중첩되는 모든 타이밍의 입력 보존까지 검증했다고 주장하지 않습니다.

같은 최종 릴리스에서 JS 로드를 보류하고 React props가 아직 없는 SSR 입력창에 `첫 입력`을 타이핑했습니다. JS를 재개한 뒤 입력 보존·제출과 URL의 `search`, 기존 `mode=preview&keep=1` 유지를 확인했고 page error는 0개였습니다. 이 기능 검사는 정상 로딩 성능 표본과 구분합니다.

warm 경로가 선택된 상태에서 원본 응답을 늦춘 별도 기능 검사도 수행했습니다. `current.json` 응답이 **5,155ms** 걸리는 조건에서 200ms 시점에 `LoadingStatus`가 1개 보였고, 홈 검색은 **5,289ms**에 표시됐습니다. `$RC`가 true인 스트리밍 경로로 돌아갔으며 page error는 0개였습니다. 이는 20ms 이후 기존 로딩·스트리밍을 유지하는 기능 검사이며 위 30방문 성능 집계에 넣지 않습니다.

### 전송량과 출처 캐시

정상 로딩 32방문의 최소 10초 관찰에서 first-party JS는 전후 모두 **16요청**, encoded 합은 모든 조건에서 **315,680→297,053B**, **18,627B·5.90% 감소**했습니다. async 대시보드 preload도 합계에 포함하므로 동기 manifest 축소를 전체 JS 다운로드 제거로 설명하지 않습니다. 조기 입력 6방문의 제목 확인 시점에도 같은 16요청·전후 byte 합이 관측됐지만 고정 10초 표본이라고 부르지 않습니다.

| 폰트 조건 | 전 | 후 |
| --- | --- | --- |
| 한국어 모바일 warm·cold·조기 입력, 한국어 데스크톱 | 13요청·330,652B | 13요청·330,652B |
| 영어 모바일 warm | 11요청·279,196B | 11요청·279,196B |

폰트는 각 표본 안에서도 요청 수·encoded byte 합이 같았습니다. 이번 변경에 폰트 수정이나 새 의존성 추가는 없습니다. 영어 사전은 provider의 서버 props 전달을 유지하므로 JS 감소를 전체 언어 데이터 제거로 보지 않습니다. warm HTML/RSC encoded 중앙값은 한국어 **25,577→26,375B**, 영어 **48,659→47,846B**, 데스크톱 **25,575→26,375B**였습니다.

입력 없는 정상 로딩의 CLS는 전후 모두 모바일 **0.0001319935**, 데스크톱 **0.0002798209**로 같았습니다. 조기 입력은 전후 각각 3회 중 2회에서 **0.3520277281**, 1회에서 **0.0001319935**가 기록됐습니다. 검색 결과 화면 전환을 포함한 별도 관찰이므로 정상 초기 로딩과 합산하지 않으며, 큰 layout shift가 없었다고 표현하지 않습니다.

cold Pages replay는 매 방문 전후 모두 **7요청·gzip 1,489,670B**로 일치했습니다. warm의 upstream 기록은 방문당 값이 아니라 이전 예열을 포함한 누적 카운터입니다. 한국어 warm은 전 8건·후 7건, 영어 전 표본은 누적 9건인 3회와 통계가 초기화된 별도 묶음의 누적 3건인 2회·후는 8건인 5회, 데스크톱은 전후 모두 9건이었습니다. 각 연속 묶음 안에서 추가 요청은 관측되지 않았지만 첫 기록 이전의 예열·manifest 갱신 수와 묶음 초기화가 다릅니다. 누적 건수가 같거나 모든 방문의 원본 조회 타이밍까지 같았다고 주장하지 않습니다.

조기 입력은 양쪽 첫 회차에서 manifest 요청이 진행 중이었고 다음 기록에 학사 공지 **236,531B**·AI 메타데이터 **1,103,943B**의 버전 JSON 두 요청이 추가됐습니다. 추가된 두 원본의 종류·크기는 같지만 앞선 누적 manifest 수가 달라 총 누적 건수·byte는 전후 같지 않습니다. 원본 버전 고정과 매 방문의 캐시·갱신 타이밍까지 동일하다는 주장은 구분합니다.

### 원인 확인과 경계 선택

- 원시 LCP 요소는 전후 동일했습니다. 한국어·영어 모바일은 첫 공지의 제목 `H3`, 데스크톱은 같은 공지의 AI 요약 `P`입니다. 로고나 더 큰 새 요소로 후보가 바뀌어서 생긴 차이로 설명하지 않습니다.
- 별도 전 데스크톱 진단에서 FCP **312ms**, React 본문 교체 예약 `$RC` **296.9/297.6ms**, 실제 교체 `$RV` **664.8ms**, 본문 가시화 **746.7ms**, LCP **776ms**를 관측했습니다. 이 진단은 정식 성능 표본에 넣지 않았습니다.
- 설치된 React 서버는 **완료된 Suspense 내용도** 누적 출력 크기가 기본 `progressiveChunkSize` **12,800B**를 넘는 등의 조건에서 fallback과 숨김 segment로 나누어 출력합니다. 이어지는 교체 스크립트에는 `$RT + 300`을 기준으로 예약하는 경로가 있습니다. 본문 수신 완료와 실제 표시가 분리됐으며, 모든 방문에 고정 300ms가 붙는다는 뜻은 아닙니다.
- 진단용 시안에서 서버 대시보드를 동기 렌더하도록 바꾸어도 큰 내부 fallback이 남았습니다. 실제 warm 5회의 데이터 준비는 **약 10–13ms**, 외부 데이터 fallback은 0회이고 내부 fallback만 표시됐습니다. warm 데이터의 20ms timeout 초과를 이 현상의 원인으로 채택하지 않았습니다. 전용 진단 수정은 최종 빌드에 남기지 않았습니다.
- [공식 React Activity 안내](https://react.dev/reference/react/Activity#speeding-up-interactions-during-page-load)는 항상 보이는 Activity도 초기 HTML을 유지하며 Selective Hydration에 참여할 수 있다고 설명합니다. 설치된 React 19.3의 공개 API를 사용해 데이터 완료 뒤 대시보드 경계만 바꿨습니다. 후 별도 데스크톱 진단은 교체 예약 호출 없이 **FCP=LCP 372ms**였습니다. 이 한 방문을 중앙값 개선 폭으로 사용하지 않습니다.

첫 cold와 느린 warm 데이터는 기존 외부 Suspense로 스트리밍하고, 20ms 안에 데이터가 준비되면 직접 반환합니다. **20ms는 데이터 준비 경로의 예산이며 전체 SSR·TTFB 상한이 아닙니다.** Activity는 오류 경계가 아니므로 warm 대시보드의 SSR 모듈·렌더 실패는 기존 내부 Suspense의 클라이언트 재시도 대신 상위 `app/error` 범위의 복구가 될 수 있습니다. 모든 SSR 실패 상황의 복구 동등성까지 입증한 변경은 아닙니다.

검색에도 Suspense를 추가하거나 대시보드 경계를 여러 개로 나눈 시안은 표시 지연·검색창 이동 또는 JS 보류 중 검색 준비 실패가 남아 철회했습니다. 서버/브라우저 조건부 renderer, 동기 `require`, React 내부 코드·비공개 크기 설정을 최종 제품 코드에 추가하지 않았습니다.

- **지금은 계획·로컬 작업만 진행**합니다. 운영 부하 테스트, 반복 Lighthouse/PSI, cache-busting query, 반복 cold 유도, 운영 API polling, Preview별 성능 비교와 실험마다 push/merge하는 방식은 사용하지 않습니다.
- 저장소의 `Sync to Vercel Repository` workflow는 main CI 성공 후 동기화 경로가 있습니다. 수정은 로컬에서 모아 검증하고, 원격 반영 전에 실제 연결의 Preview 자동 배포 여부를 읽기 전용으로 확인합니다. 이 문서의 계획만으로 프로젝트 설정·자동화를 임의 변경하지 않습니다.
- 이후 배포 요청 시 검증된 변경을 한 번에 반영해 **운영 배포 1회**를 목표로 합니다. 소스 SHA·CI·배포 연결을 확인한 뒤 KO/EN 홈 각 1진입, 검색 1시나리오, 시간표 1진입·강의 추가, 이미 연 화면의 설치/이메일 확인으로 smoke를 제한합니다. 이것은 페이지/시나리오 수 제한이며 내부 API 요청 수나 Fluid CPU 사용 시간을 보장하지 않습니다.
- 사전에 로컬 network 기록으로 smoke의 자동 query/refetch를 파악합니다. 운영에서 오류나 지연이 보이면 반복 재현을 중지하고 기존 로그·로컬 fixture로 돌아갑니다. 운영에서 cold 상태를 만들거나 다국어·기기별 성능 표본을 다시 수집하지 않습니다.
- 남은 약 1시간을 테스트 가능 횟수나 관찰 시간으로 환산하지 않습니다. 운영 트래픽과 복구 여유를 남기며, 실제 사용량을 새로 확인하지 못하면 추가 배포·운영 검증을 보류합니다. 테스트를 위해 요금제·비용 상한·캐시·보안 설정을 변경하지 않습니다.

계획 작성 당시 미실시 항목은 새 코드 수정·실행 테스트·운영 배포·실기기·OS 설치·운영 Sentry/GA/이메일/푸시 수신이었습니다. 이후 로컬 실행은 마지막 결과 절에 기록합니다. 이미 통과한 로컬 기능을 운영 확인 완료로 바꾸지 않으며, 기존 40방문의 불리한 회차와 console 오류도 유지합니다.

#### W3. cold JSON과 서버 CPU 비용 축소

**대상:** [공지 조회](../lib/server/announcements.ts), [AI 부착](../lib/server/announcement-ai.ts), [원본/캐시](../lib/server/crawl-data.ts). 발행 형식 변경이 실제로 필요할 때만 [생성기](../scripts/generate_announcement_ai_summaries.mjs), [발행기](../scripts/publish-crawl-data.ts), [manifest 계약](../lib/crawl-data-contract.ts)까지 범위를 넓힙니다.

1. **프로파일:** 동일 fixture의 새 Node에서 cold 1회와 직후 warm을 진단하고 네트워크 대기와 JSON decode/parse·SHA 검증·정렬·AI hash 결합을 분리합니다. 요청별 bytes, 프로세스 CPU, RSS/heap, 완료 시각을 기록합니다. 프로세스 전체 시간과 특정 함수 CPU를 혼동하지 않고 운영 CPU 사용량으로 환산하지 않습니다.
2. **기존 캐시 우선:** version별 parsed Promise 공유·최대 24개 제한, 60초 metadata Promise 캐시, 실패한 원본 Promise 제거·재시도와 동시 호출을 확인합니다. 중복 읽기/파싱이 실제로 발견되면 해당 경로를 한 번 수정합니다. TTL을 늘리거나 Next 캐시 상한을 우회해 비용을 숨기지 않습니다.
3. **발행 단계 후보:** 원본 양이 지배적이면 `publish-crawl-data.ts`의 기존 `buildLocalSnapshot`/`readValidatedJson`을 재사용해 AI 파일을 의미가 같은 compact JSON으로 발행하는 가장 작은 후보부터 비교합니다. 파일명·version·모든 필드는 유지하고 바뀐 bytes로 size/SHA를 계산합니다. 생성 fingerprint·input/detail hash·provider 등은 다음 생성의 재사용 판단에 필요할 수 있어 삭제하지 않습니다. 홈 전용 소형 snapshot은 이것으로 부족할 때만 검토하며 새 파일명·스키마를 미리 확정하지 않습니다. 이미 생성된 데이터를 이용하고 계획/성능 테스트를 위해 OpenAI 재생성이나 크롤러를 실행하지 않습니다.
4. **호환 조건:** 소형 발행물을 선택하면 생성/정렬 규칙, 원본 version·size·SHA, AI source hash의 전체 본문 일치, 구 manifest와 새 코드·새 manifest와 구 코드, 파일 누락·불일치·rollback을 설계합니다. 생성기의 important/pinned 우선순위와 홈 날짜 정렬이 다르므로 생성 단계에서 임의로 12개만 자르지 않습니다. 구 코드가 알지 못하는 manifest/source-health 항목으로 전체 검증이 실패하지 않게 발행 순서를 검토합니다. 홈 최종 요약뿐 아니라 공지 목록·검색·상세·공모전·IndexNow snapshot의 호출 계약과 summary API HTTP 캐시도 유지합니다. 새 자료가 없거나 잘못된 경우 기존 full metadata로 안전하게 복귀해야 합니다.
5. **관련 검사:** `lib/server/announcements.test.ts`, `announcement-ai.test.ts`, `crawl-data.test.ts`, `lib/crawl-data-contract.test.ts`를 사용합니다. 발행 코드를 바꾼 경우에만 `scripts/publish-crawl-data.test.ts`, `generate_announcement_ai_summaries.test.mjs`와 daily crawl/IndexNow 관련 검사·dry-run fixture까지 넓힙니다. 정상/빈 데이터/metadata 실패/canonical·legacy hash/TTL 직전·직후/동시 요청/새 version, 의미 동일성·연락처 제거·변경 없는 발행 생략·부분 실패 시 원본 복원·rollback을 포함합니다.

### W0. 기준선 보존과 로컬 차단 환경

### W1. 조기 검색의 화면 이동과 오류 복구

조기 제출 뒤 짧은 검색 로딩 화면 아래에 `NotificationPermissionPrompt`가 나타났다가 검색 결과가 길어지며 화면 밖으로 밀리는 흐름을 확인했습니다. layout-shift의 source는 알림 `<section>`이었고, 결과 화면 전환 후 안내가 viewport 안에 들어왔다가 나가는 entry를 구분했습니다. 기존 0.352는 최근 입력을 제외한 전체 관찰 구간의 이동량 합계였으므로 공식 CWV CLS로 부르지 않습니다. 새 진단에는 entry별 source·rect·최근 입력·경로·입력/제출/제목 표시 시각과 관찰 구간의 최대 세션 윈도 값을 함께 기록했습니다.

[SearchResultsView](../app/features/home/SearchResultsView.tsx)의 결과 영역에 `min-h-svh`를 적용해 loading·0건·실패·결과 상태 모두 최소 한 화면 높이를 유지하게 했습니다. 알림 안내는 기존 문서 흐름에 남아 스크롤로 접근할 수 있습니다. 검색창을 공통 상위 구조로 옮기거나 알림을 숨기지 않았으며, 제출 후 결과 검색창으로 바뀌는 기존 설계도 유지했습니다. 원래 빌드에 같은 높이 규칙만 주입한 진단에서 큰 알림 이동이 사라진 것을 확인했지만 이를 최종 제품의 유효 전후 성능 비교로 사용하지 않습니다.

페이지 오류 복구에서는 설치된 Next.js 16.4 문서와 구현의 `retry`를 사용하도록 [페이지 오류 UI](../app/error.tsx)와 [전역 오류 UI](../app/global-error.tsx)를 수정했습니다. 이전 `reset`은 이미 실패한 서버 payload의 재렌더만 시도해 test-only SSR 장애를 제거한 뒤에도 오류 화면이 남았습니다. `retry`는 서버 내용을 다시 요청하며, 초기 로컬 회귀에서 KO/EN 오류 화면이 장애 제거 뒤 버튼 한 번으로 복구됐습니다.

클라이언트 chunk 실패는 `retry`만으로 복구되지 않는 별도 경로였습니다. 오류 이름이 `ChunkLoadError`일 때만 사용자가 재시도 버튼을 클릭하면 `window.location.reload()`를 호출합니다. 다른 오류는 `retry`를 유지하고 자동 새로고침은 추가하지 않았습니다. 선택적 오류 이름 접근과 Sentry `captureException`을 유지했으며, 초기 로컬 회귀에서 KO/EN chunk 차단 해제 후 명시적 클릭으로 홈이 복구되고 기존 URL의 query도 유지됐습니다. 이 fault 검사는 실제 운영에 예외를 발생시키지 않고 로컬 빌드에만 주입했습니다.

### W2. GA·CSP와 개인정보 계약

분석 bootstrap과 CSP의 제품 코드는 유지했습니다. 추가 테스트에서 공개 경로의 queue·`gtag` 함수·`window.load` 후 4초 지연, query/hash 제거, 모임 초대 referrer의 origin 축약과 민감 경로의 분석 차단을 검사했습니다. CSP는 공개 태그 script와 기존 GA collect origin을 유지하고 Google 태그 연결의 wildcard·광범위 허용을 추가하지 않았습니다.

이번 로컬 브라우저의 외부 gtag 응답은 작은 stub으로 대체했습니다. 따라서 queue·개인정보 필터의 단위 계약과 로컬 가로채기 범위를 확인한 것이며 실제 gtag의 이벤트 생성·GA 수신을 검증한 것은 아닙니다. 앞선 40방문에서 보인 `/td` CSP 거부 6건은 기존 기록에 남깁니다. 해당 거부를 제거하기 위해 정책을 넓히거나 console 오류를 숨기지 않았고, 자연 발생 빈도와 필수 분석 수신의 운영 상태도 확정하지 않았습니다.

### W3. AI metadata의 발행 바이트 축소

[발행기](../scripts/publish-crawl-data.ts)의 `readValidatedJson`에서 검증을 통과한 `announcement-ai-metadata.json`만 compact JSON으로 발행하도록 변경했습니다. 고정 자료에서 원문 바이트는 **5,414,894→4,418,112B**, gzip level 6은 **1,103,943→1,044,195B**입니다. 이는 같은 자료의 직렬화 결과이며 브라우저 로딩 시간 비교값이 아닙니다.

모든 필드를 보존하고 변환 후 바이트로 manifest의 size·SHA-256을 계산합니다. AI 요약·정렬·전체 원문 hash 검증과 생성 fingerprint·input/detail hash·provider 등 재사용 정보도 유지했습니다. 생성 원본 파일과 다른 JSON 파일의 바이트는 그대로 두며, 기존 버전 다운로드·보존·rollback에서는 manifest가 가리키는 원래 바이트를 검증합니다. 새 홈 전용 schema나 축약 snapshot, AI 재생성은 추가하지 않았습니다.

발행 테스트에는 의미와 필드의 동일성, 변환 후 size/hash, 로컬 원본 보존, 포맷만 다른 자료의 발행 생략, 기존 pretty JSON에서 compact로 전환한 뒤 구버전의 정확한 바이트 보존·rollback, 잘못된 데이터 거부를 추가했습니다. 런타임의 TTL·진행 중 Promise 공유·실패 복구·AI 최종 await는 유지합니다.

초기 Node 프로파일 구간에는 대기와 진단 도구 실패가 섞여 있어 다운로드·JSON parse·SHA·SSR의 CPU 기여를 정확히 분리하지 못했습니다. 별도 JSON parse 진단도 전체 서버 요청의 CPU를 대신하지 않습니다. 이 결과로 **전체 SSR CPU 또는 Vercel Fluid CPU가 줄었다고 판단하지 않습니다.** compact 발행 뒤에도 큰 JSON 다운로드·검증·파싱과 느린 metadata의 최종 대기는 남습니다.

### W4. FCP·warm 경계 편차는 기존 구현 유지

검색과 대시보드의 JS 분리, `Activity mode="visible"`, cold 경로와 warm 20ms 경계, 폰트 구성은 유지했습니다. 글꼴 전체 preload·guard 수치 증가·다른 렌더 경계를 추가하지 않았습니다. 기존 desktop FCP 중앙값 +8ms와 native layout·warm 경로 편차만으로 추가 구조 변경을 선택하지 않았으며 원인별 안정적인 개선을 확정하지 않았습니다.

#### 이번 변경의 채택 판단과 W4 후속

이번 배치는 **원본 발행 바이트 축소, 조기 검색의 불필요한 화면 이동 해소, 오류 재시도와 접근성 보완**을 위한 수정으로 채택했습니다. 검색 준비·FCP·LCP·Node CPU의 일관된 추가 개선은 확인하지 못했고, 불리한 cold 준비·LCP·CPU, 데스크톱 LCP와 조기 입력 FCP도 결과에 포함했습니다. 범위가 겹치는 조건별 5회 표본을 통계적 유의성이나 운영 p75로 해석하지 않습니다.

W4의 남은 font/native layout·20ms 경로 편차와 cold CPU 증가 원인은 별도 추적 대상으로 유지합니다. 측정치 하나를 맞추기 위한 guard 증가·일괄 preload·오류 보호 생략은 적용하지 않았습니다. 이 50방문의 성능 관찰은 앞 절의 fallback 조건 기능 회귀와 별도로 보존하며, 후속 기능 검증이나 운영 배포 완료를 의미하지 않습니다.

남은 검증은 실제 OS 설치 승인·실기기, 운영 GA/Sentry/이메일·푸시 수신과 운영 배포입니다. cold 데이터 실패·warm Promise의 20ms 전후 실패·metadata만 실패는 단위 테스트에서 확인했으며 이번 브라우저 render/chunk fault와 동일한 검사로 취급하지 않습니다. 전체 `npm run check`의 Python 연쇄 검사는 실행하지 않았습니다. `/td` 차단의 필요성, cold CPU 증가와 첫 표시 편차, 원래 감사의 작은 선택 상태·외부 이동·지도·모임·로고 항목은 남아 있습니다. 이 로컬 검증 단계에서는 Vercel 배포·운영 요청과 push/PR을 실행하지 않았습니다.

### 후속 변경 제출 범위

이후 사용자의 별도 요청에 따른 변경 제출은 기능별 커밋·작업 브랜치 push·PR 생성까지이며, main 머지·Vercel 배포·운영 요청은 포함하지 않습니다. 기준 브랜치의 PR #254(`55b47d1`)에 이미 포함된 도서관 좌석 지도 변경은 이번 수정에서 제외합니다. 해당 파일의 작업 내용은 기준 브랜치와 동일하므로 기존 로컬 검증의 제품 소스는 그대로입니다.

커밋은 오류 복구, 초기 설치 이벤트 보존, 홈 검색·다국어 의존성, Sentry tracing 제거, AI metadata 선행 조회, JSON 발행 바이트 축소, 접근성·일정 이동, 분석 계약 테스트, 문서로 나눕니다. 기존 로컬 성능 표본은 위에 명시한 중간 빌드 사이의 비교이므로 PR 전체와 main의 전후 비교로 바꾸지 않습니다. 반복 푸시로 검사 실행을 늘리지 않으며 GitHub의 PR 자동 검사와 Vercel 운영 검증도 구분합니다.
