# 디자인·사용성·로딩 성능 점검

2026-10-18 기준. 버튼·로고 디자인과 초기 로딩 문의에서 시작한 조사 및 수정 결과를 현행 상태 중심으로 정리했습니다. 최초 운영 화면 관찰, 코드 분석, 이후 로컬 production 비교를 구분합니다. 문서 정리 과정에서 과거 수치를 새로 측정한 것처럼 갱신하지 않았습니다.

불편을 설명하는 근거는 조작 요소와 정적 카드의 불명확한 구분, 작은 조작 영역·문자, 핵심 메뉴까지 긴 이동, 축소 시 로고 식별성, 화면별 표현 차이입니다. 입력 소실은 기능 문제이며 로고의 미적 선호는 사용자 시안 비교가 필요한 가설입니다.

## 시간표 성능 비교 기록

아래 시간표 표는 **기존 작업에서 실행한 로컬 측정**입니다. 메뉴·문서 정리 당시 재수집하지 않았으며, 이후 홈 캐시 측정은 별도 절에 기록합니다. 단계마다 대조군·SDK 조건이 다르므로 누적 개선율을 계산하지 않습니다. 재측정은 [성능 가이드](../PERFORMANCE.md)를 따릅니다.

### 공통 다국어 JS·Sentry 단계의 조건

Next.js 16.4.1 Turbopack production build/start, 같은 Windows 호스트, Chromium 155.0.8059.80, 390×844. 다운로드 200,000B/s·업로드 93,750B/s·추가 latency 0ms·CPU slowdown 4. 매 회 새 context의 빈 HTTP 캐시를 사용하되 HTTP/preload 재사용은 허용하고 서비스워커는 차단했습니다. 브라우저 interception 대신 로컬 압축 프록시를 사용했습니다.

전·후 모두 로컬 가짜 DSN으로 **실제 Sentry SDK 활성화**, 외부 ingest 없음. 배치 전 API와 해당 언어 SSR 각 1회 warmup, 측정 중 build/test/profile 정지. 강의 1,526개·JSON 696,996B·gzip level 6의 55,596B, SHA-256 `4ab295f3ec37dc65a944caecebe56d88ff1956466dd59a1052ad5dbec54c4d30`이 네 배치에서 일치했습니다. KO/EN 각각 전 5회·후 5회, 느린 회차도 포함합니다.

버튼 준비는 보이는 버튼에 React click handler가 연결된 첫 rAF입니다. 클릭 반응은 trusted pointerdown부터 모달 첫 article box를 감지한 rAF까지입니다. 진입→첫 결과에는 자동화 클릭 왕복 대기도 들어갑니다. SDK 보호는 global error/rejection handler의 SDK 표식이 처음 관측된 프레임이며 init 소요 시간과 다릅니다. 픽셀 표시 완료·INP·실기기 P95는 아닙니다.

### 공통 다국어 JS·Sentry 단계의 결과

[경로 함수](../lib/i18n/routing.ts)와 ko/en 사전, [client context](../app/components/LocaleContext.tsx), [서버 provider](../app/components/LocaleProvider.tsx)를 분리했습니다. 한국어 기본값과 기존 dictionary/경로 API·문구·중첩 구조·query/hash를 유지합니다. 영어 사전은 서버 props로 전달하므로 HTML/RSC도 함께 봅니다.

[Sentry init](../instrumentation-client.ts)은 동기 실행과 기본 integration 14개·privacy/router hook을 유지하고 미사용 logs/metrics만 껐습니다. handler 6개가 제거됐고 나머지 hook 9개·handler 13개는 유지됐습니다. ## 대용량 JSON 캐시·홈 초기 로딩 조사와 최종 수정 — 2026-10-18

### 원인과 적용 범위

설치된 Next.js 16.4.1의 `patch-fetch.js`는 fetch 응답 본문을 모두 읽어 Base64로 직렬화합니다. `incremental-cache/index.js`는 이 항목의 `JSON.stringify(data).length`가 2MiB를 넘으면 production에서 경고를 내고 저장하지 않습니다. 기존 버전 JSON 요청은 모두 `force-cache`여서 저장할 수 없는 큰 응답에도 이 과정을 반복했습니다. 경고를 숨기거나 원본 크기 제한을 올려 해결할 수 있는 문제가 아닙니다.

고정한 공개 데이터에서 학사 공지는 원본 **1,673,940B**, AI metadata는 **5,391,760B**였습니다. 전자의 원본은 2MiB보다 작지만 각각 **2,232,304B·7,189,403B**의 직렬화 항목이 되어 저장에 실패했습니다. 앞선 운영 응답 관찰과 replay의 수치 차이는 응답 metadata도 직렬화하기 때문이며 두 기록을 JSON 원본 크기로 해석하지 않습니다.

- [crawl-data](../lib/server/crawl-data.ts)는 검증된 manifest의 raw `entry.size`가 **1MiB 초과**이면 `no-store`, 이하면 기존 `force-cache`를 사용합니다. Base64 증가분·metadata 여유를 둔 보수적 정책입니다. manifest 자체의 `no-store`와 60초 메모리 캐시, 버전별 최대 24개 Promise 캐시·동시 요청 공유, timeout·크기·SHA-256·구조 검증·출처 상태·번들 fallback·실패 후 재시도는 유지합니다.
- [홈](../app/page.tsx)·[본문](../app/features/home/HomePageClient.tsx)·스켈레톤은 조사 시작 당시 구조로 복원했습니다. 한국어와 영어 모두 검색·메뉴가 기존 7개 데이터 경계를 공유합니다. 이전 사용자 요청의 6개 메뉴 구성·순서는 유지하며, 직접 `?search` 진입도 기존 검색 화면을 사용합니다. 조기 표시 UI 시안은 최종 적용 범위에서 제외했습니다.
- 공용 [SearchBar](../app/components/SearchBar.tsx)는 hydration 전 입력과 첫 effect 직전 입력을 보존합니다. DOM 값을 React state로 채택하되 이미 큐된 입력 갱신을 우선하며, 초기 DOM 값이 기본값과 같으면 불필요한 setState 호출을 생략합니다. 검색 버튼 활성화·제출·초기화·자동 검색 부모 조건과 실제 `defaultValue` 변경은 계속 동기화합니다.

### 결과 해석과 남은 비용

- 모바일 server warm의 LCP 중앙값은 **1,780→1,416ms, 20.4% 단축**됐습니다. 검색 handler 준비 대리지표도 **4,423→4,198ms, 5.1% 단축**됐지만 여전히 약 4.2초입니다. 해당 두 지표는 이 5회 표본에서 전후 범위도 겹치지 않았습니다.
- 같은 조건의 FCP는 **1,172→1,416ms로 244ms 늦어졌습니다.** warm 경로에서 먼저 스켈레톤을 표시하는 대신 준비된 본문을 직접 반환하면서 첫 콘텐츠와 주요 본문을 함께 표시하는 교환관계가 있습니다. 모든 표시 지표가 좋아진 변경으로 설명하지 않습니다. TTFB 중앙값도 **28→39.7ms**로 늘었습니다.
- 모바일 server cold의 검색 handler 준비 대리지표는 **4,472.9→4,469.2ms**로 같은 수준입니다. LCP는 **2,768→2,688ms**였지만 전후 범위가 겹쳐 안정적인 개선을 입증하지 못했습니다. 빠르거나 느린 한 회차를 제외하지 않았습니다.
- 데스크톱 server warm의 LCP 중앙값은 **704→352ms**였지만 FCP는 **300→352ms**, 검색 handler 준비는 **771.8→798ms로 26.2ms 늦어졌습니다.** 준비 시간의 범위도 겹칩니다. 데스크톱의 조작 준비 개선으로 해석하지 않습니다.
- 홈 SSR reveal 스크립트 관측은 모바일 warm·데스크톱 warm 각각 전 **5/5 true → 후 5/5 false**, 모바일 cold는 전후 모두 **5/5 true**였습니다. 직접 반환 경로가 warm fallback 교체를 피한 관측과 일치합니다. 브라우저 CPU·hydration 비용 전체를 제거했다는 증거는 아닙니다.

최종 30방문의 폰트는 모두 **13요청·330,652B**, first-party JS는 모두 **16요청·322,426B**로 같았습니다. cold Pages upstream도 전후 모두 **8요청·gzip 1,486,500B**였고 같은 프로세스의 warm 방문에서 추가 요청은 **0건·0B**였습니다. warm 기록의 upstream 누적 카운터와 그 방문의 추가 요청량을 구분합니다. 이번 효과를 폰트·JS·원본 JSON 다운로드 총량 감소로 설명하지 않습니다.

공통 JS 실행과 hydration·CPU 스케줄링 비용은 남습니다. 5회 표본과 로컬 호스트 상태만으로 통계적 유의성·실사용자 p75/P95·실기기 성능을 확정하지 않습니다. 날짜를 고정한 주말 안내의 LCP 결과를 평일 식단·셔틀 상태나 다른 viewport의 LCP 요소로 일반화하지 않습니다.

### 이 배치에서 확인한 기능과 검증 한계

[홈 경로 단위 회귀](../app/page.test.tsx) **6개가 통과**했습니다. 최초 cold의 동기 경계·타이머 미생성, 7개 조회 완료 후 전환, 최초 실패 후 경계 유지, 빠른 warm의 동일 props·타이머 정리, 20ms 후 같은 Promise 스트리밍, 빠른·늦은 오류 전파를 검증합니다. 앞선 cache-only 절의 전체 검사 수치를 이번 렌더링 변경의 전체 회귀 검증으로 대신하지 않습니다.

helper 추출을 포함한 소스에서 전체 단위 테스트 **144개 파일·1,208개 테스트가 통과**했습니다(59.39초). 집중 홈 회귀 6개, 타입 검사와 변경한 2개 파일의 ESLint, 전체 lint와 다국어 검사도 통과했습니다.

최종 로컬 릴리스는 기존 `.env.local`의 DSN 설정을 유지하고 테스트 DSN으로 덮어쓰지 않은 상태에서 빌드했습니다. 업로드 토큰만 비워 실행한 `npm run build`는 **61/61** 생성으로 성공했고 BUILD_ID는 **`UdVLG1VR7wou4YbcGU9fB`**입니다. 생성된 `next-env.d.ts`를 기존 bytes로 복원한 뒤 최종 `npm run type-check`도 종료 코드 0이었습니다. 이 빌드는 helper 추출 후의 릴리스이며 앞선 가짜 DSN 계측 빌드와 구분합니다. 릴리스 빌드를 새로 실행했다는 사실로 위 성능 표를 다시 측정한 것처럼 바꾸지 않습니다.

이 릴리스에서 KO/EN 각각 320·390·1440px의 **6개 조건**을 실제 브라우저로 확인했습니다. 메뉴 순서·href·영어 경로 prefix, 필터 `aria-pressed`, 검색어 삭제·Enter 제출·결과 query·초기화·뒤로가기 복원과 도서관 이동 후 복귀가 통과했습니다. 메뉴의 관측 최소 크기는 **85.3×92px**였고 가로 넘침·page error·console error는 6개 조건 모두 0개였습니다.

처음 두 자동화 실행은 검색어 삭제 직후 바로 다시 입력하는 과정에서 query가 빈 값이고 제출 버튼이 disabled인 상태로 남아 URL 변경 대기 30초가 실패했습니다. 이후 삭제 후 disabled, 재입력 후 enabled를 각각 확인하는 상태 대기를 사용해 6개 조건을 완료했습니다. 이 과정에서 제품 소스는 바꾸지 않았습니다. 삭제·재입력이 중첩되는 모든 타이밍의 입력 보존까지 검증했다고 주장하지 않습니다.

같은 최종 릴리스에서 JS 로드를 보류하고 React props가 아직 없는 SSR 입력창에 `첫 입력`을 타이핑했습니다. JS를 재개한 뒤 입력 보존·제출과 URL의 `search`, 기존 `mode=preview&keep=1` 유지를 확인했고 page error는 0개였습니다. 이 기능 검사는 정상 로딩 성능 표본과 구분합니다.

warm 경로가 선택된 상태에서 원본 응답을 늦춘 별도 기능 검사도 수행했습니다. `current.json` 응답이 **5,155ms** 걸리는 조건에서 200ms 시점에 `LoadingStatus`가 1개 보였고, 홈 검색은 **5,289ms**에 표시됐습니다. `$RC`가 true인 스트리밍 경로로 돌아갔으며 page error는 0개였습니다. 이는 20ms 이후 기존 로딩·스트리밍을 유지하는 기능 검사이며 위 30방문 성능 집계에 넣지 않습니다.
