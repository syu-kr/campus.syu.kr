## 문의·제보 원문 보존과 전용 필드의 수동 정리

담당자는 개인정보처리방침 제9조의 개인정보 보호책임자인 단독 운영자이며, 접수는 사이트 하단 문의 버튼 또는 해당 이메일로 받습니다. 독립 대체관리자는 지정되어 있지 않습니다. [11월 4일 사전 공지](../public/service-notices/022-submission-retention.md)에 따라 2026년 12월 5일 00:00 KST부터 `site_inquiries`와 `campus_tip_suggestions`는 어떤 질문·제보가 있었는지 참고하기 위해 완료·기각 처리 후 1년간 원문과 그 안의 AI 분류 결과를 보존하는 기준을 적용합니다. 그 전까지 기존 ‘서비스 개선 검토 목적 달성 시까지 보존하며, 운영상 필요가 없어진 경우 삭제’ 기준을 유지합니다. 기존 자료에 새 기간을 일괄 소급하지 않으며 기존 목적과 적법한 보존 근거를 별도로 확인합니다. 새 기준에서 1년이 지난 뒤에는 필요한 내용만 개인정보를 제거한 기록으로 남기고 원문과 포함된 AI 결과를 수동으로 파기합니다. 원문 안에도 연락처·학번·상세 URL 등이 있을 수 있으므로 전용 필드 정리만으로 익명 자료가 되지는 않습니다.

관리자 상태 변경은 원문 삭제나 전용 필드 정리를 실행하지 않습니다. 새로 완료·기각 상태에 진입할 때 트랜잭션에서 `closed_at`을 기록하고, 같은 상태 재저장이나 완료↔기각 변경으로 그 시점을 연장하지 않습니다. 다시 검토 상태로 열면 `closed_at`을 지우며 다음 완료·기각 때 새 처리 시점을 기록합니다. 관리자 상세의 ‘완료·기각일’은 서버 기록을 표시하며, 기존 완료·기각 자료에 날짜가 없으면 ‘기록 없음 · 처리 기록 확인 필요’로 안내합니다. `updated_at`은 상태 재저장으로 바뀔 수 있어 보존 시작일로 대신 쓰지 않습니다. 기존 완료·기각 자료에 `closed_at`이 없으면 과거 감사 기록의 상태 전환이나 비공개 처리 기록으로 실제 완료일을 확인합니다. 실행일·생성일을 완료일로 임의 소급하지 않고, 확인되지 않은 건은 담당자가 증거 확인과 다음 점검 시점을 남깁니다.

완료·기각 처리 시 담당자는 연락·검토가 끝났는지 확인하고 전용 `contact`·`user_agent` 필드를 수동 정리합니다. 연락이 계속 필요한 건은 검토 중 상태와 처리 사유를 확인한 뒤 정리 대상에서 제외합니다. 기존 완료·기각 자료도 같은 기준으로 점검합니다. 아래 스크립트는 원문·AI 결과·상태·완료일을 변경하지 않고 이 두 전용 필드만 제거합니다. 기본 실행과 `--dry-run`은 읽기 전용이며 예약 작업에는 연결하지 않습니다.

```bash
npx ts-node --project tsconfig.json scripts/cleanup_submission_metadata.ts --dry-run
npx ts-node --project tsconfig.json scripts/cleanup_submission_metadata.ts --apply
npx ts-node --project tsconfig.json scripts/cleanup_submission_metadata.ts --dry-run
```

실행 전 담당자가 서비스 계정의 대상 프로젝트, 완료·기각 대상과 예외, 첫 dry-run의 집계 건수를 확인합니다. 출력은 대상·전용 필드·실제 업데이트 건수뿐이며 문서 ID·본문·연락처·브라우저 값은 출력하지 않습니다. `nonemptyContacts`는 내용이 있는 연락처 수이고 `contactFields`에는 빈 값도 포함됩니다. 적용은 조회 당시 `updateTime`을 전제로 하므로 동시에 재검토·수정한 문서가 있으면 해당 페이지 전체를 중단합니다. 앞서 성공한 페이지는 남을 수 있으므로 실패하면 부분 처리 가능성을 기록하고 상태·예외를 다시 확인한 뒤 dry-run부터 재시작합니다. 적용 후 dry-run의 후보 0과 원문·AI 결과·상태가 보존됐는지를 관리자 조회로 확인합니다. 처리 기록에는 실행 시각·환경·SHA·담당·집계·오류 여부를 남기며 원문이나 식별자를 공개 로그에 복사하지 않습니다.

원문 보존은 담당자가 완료일과 1년 도래 대상을 수동 점검합니다. 필요한 이력만 남길 때는 제목·본문·URL·메모·AI 결과에 포함된 개인정보도 함께 검토하며, 전용 필드만 삭제한 원문을 그대로 옮기지 않습니다. 법령상 별도 보존이 필요한 경우에는 적용 근거·항목·종료 기준을 확인하고 구분해 보관합니다. 파기 기록에는 처리일·담당·종류·건수·예외 사유를 남기고 본문·연락처를 복사하지 않습니다. 별도 `admin_audit_logs`는 자체 최대 365일 기준과 예약 정리를 따르므로 문의 원문과 한꺼번에 지우지 않습니다. 원문 자동 파기와 이 스크립트에 의한 원문 일괄 삭제는 없습니다.

권리 요청은 일반 개선 제안의 개별 답장 정책과 구별해 접수·본인 확인·대상 조사·처리 또는 제한 사유·결과 통지를 추적합니다. 룸메이트 글·세션 삭제와 Firebase Auth 사용자 삭제는 별도이며 다른 기능·공유 관리자 계정의 영향을 확인합니다. 원문과 처리 증거는 공개 Issue·PR에 올리지 않습니다.

## 신고 확인과 예약 정리의 운영 목표

개인정보 보호책임자인 단독 운영자가 새 룸메이트 신고와 권리 요청, 만료 정리 workflow의 최근 성공·실패·지연을 적어도 하루 한 번 확인하는 것을 운영 목표로 정합니다. 이는 과거에 매일 확인했거나 실제 경보를 수신했다는 증거가 아닙니다. 긴급한 노출·위협을 확인하면 다음 정기 확인을 기다리지 않고 관리자 숨김·삭제·작성 보류와 기존 사고 대응 절차를 검토합니다. 독립 대체자가 없어 운영자 부재 중에는 확인·대응이 지연될 수 있습니다. 신고가 자동 알림·자동 숨김으로 처리된다고 가정하지 않습니다.

예정된 정리 실행이 누락·실패했거나 이전 실행이 계속 진행 중이면 실행 시각·source SHA·마지막 성공·오류와 집계 건수를 확인합니다. 동시 실행·동시 갱신 충돌과 서비스 계정 설정을 확인하고, 재실행이 필요한 경우 기존 정리 명령의 대상을 검토한 뒤 운영자가 처리합니다. 작업 예약은 매일 03:30 KST이지만 실제 시작과 물리 삭제는 지연될 수 있으므로 24시간 이내 물리 삭제를 보장하지 않습니다. 실패 알림의 실수신, 지연 발견과 수동 재처리의 실제 운영 증거는 별도로 남깁니다.

룸메이트 미처리 신고도 접수 후 30일이면 기존 정리 절차의 대상입니다. 매일 확인할 때 미처리·만료 임박 건을 우선 검토하고, 이미 보존 종료된 건은 최소 감사 기록의 `미처리 상태에서 보존 종료`를 처리 완료로 바꾸지 않습니다. 본문·연락 링크를 복제해 보존을 무기한 연장하지 않으며, 신고 상태와 실제 게시글 숨김·삭제 조치 여부를 따로 확인합니다.
