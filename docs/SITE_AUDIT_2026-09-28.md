## 확인된 문제

### P1 · 검색 후 로고가 홈 화면으로 돌아가지 않음

- **재현:** 메인에서 `장학금` 검색 → 헤더 `SYU CAMPUS` 로고 클릭 → URL은 `/` 그대로이고 검색 결과가 남는다. 모바일 홈 버튼은 실제 기기에서 누르지 않았지만 같은 `/` 링크를 사용한다.
- **원인:** 검색 결과가 경로가 아닌 `HomePageClient` 내부의 `showSearchResults` 상태로 표시된다 (`app/features/home/HomePageClient.tsx:78-79, 190-197, 229-246`). 로고와 홈 버튼은 `/`로만 이동한다 (`app/components/Header.tsx:90`, `app/components/BottomNav.tsx:68`). 같은 경로 이동은 검색 상태를 초기화하지 않는다.
- **조치:** 검색을 URL 상태로 표현하거나, 현재 홈 경로에서 홈 링크를 누를 때 공통 초기화 함수를 실행한다. 로고와 모바일 홈 버튼을 함께 검증한다.

### P1 · 통합 검색의 ‘전체보기’가 검색어를 적용하지 않음

- **재현:** `장학금` 검색 결과의 ‘장학금 전체보기’ 클릭 → `/academic/scholarship?search=장학금`으로 이동하지만 검색창은 비어 있고 `1399개 항목 찾음`으로 전체 목록이 나온다.
- **원인:** `SearchResultSection`은 학사·캠퍼스·장학금 공지에만 `search` 파라미터를 전달한다 (`app/components/SearchResultSection.tsx:34-40, 63-68`). 공지 목록은 `searchQuery`를 항상 빈 문자열로 시작하고 URL 파라미터를 읽지 않는다 (`app/components/AnnouncementListPage.tsx:33, 37-44`). SW 공지·일정·연락처의 전체보기는 검색어 전달 자체가 빠져 있다. 일정·연락처 목록에도 검색 UI는 있다.
- **조치:** 전체보기 대상 목록에서 `search`를 초기 검색 상태로 읽고 URL과 동기화한다. 링크는 검색 가능한 카테고리 모두에 동일한 규칙을 적용한다.

### P2 · 같은 전화번호를 가진 부서 하나가 통합 검색에서 사라짐

- **재현:** 메인에서 `02-3399-3239` 검색 시 `SU인권센터` 1건만 표시된다. `/campus/phone`에서 같은 번호를 검색하면 `학생상담센터`와 `SU인권센터` 2건이 나온다.
- **원인:** `public/data/phone-numbers.json`에 실제로 두 부서가 같은 번호로 존재한다. 통합 검색의 중복 제거 키가 전화번호 하나라 뒤 항목만 남는다 (`lib/api.ts:354-365`).
- **조치:** 중복 제거와 결과 카드의 React 키를 모두 부서와 번호의 조합이나 원본 식별자로 바꾼다 (`app/components/SearchResultSection.tsx:71-78`).

### P2 · 통합 검색이 일치 결과 일부만 가져오면서 제한을 표시하지 않음

- **근거:** 공지 API 검색은 첫 페이지 60건만 가져온다 (`lib/api.ts:318-326`). 그 뒤 모든 출처를 합쳐 다시 100건으로 자른다 (`lib/api.ts:263-298`). 카테고리별 표시 숫자는 이 잘린 배열의 길이다 (`app/components/SearchResultSection.tsx:27-32`). 번들 공지 데이터만 대상으로 `장학금`을 찾으면 465건이 일치하지만, 운영 메인 검색은 학사 3건·SW 2건·장학금 55건으로 합계 60건만 표시했다. 운영 데이터의 정확한 전체 일치 건수는 별도 측정하지 않았다.
- **영향:** 오래된 공지나 정확히 일치하는 결과가 최근 60건 밖이면 메인 검색에 나오지 않는다. 사용자는 표시된 수를 전체 검색 결과 수로 오해할 수 있다.
- **조치:** 제한을 UI에 명시하고 카테고리 목록의 검색어 연결을 정상화한다. 전체 검색이 제품 요구라면 출처별 총건수와 페이지 조회를 사용한다.

### P2 · 일부 검색 출처가 실패해도 정상적인 ‘결과 없음’으로 보일 수 있음

- **근거:** `searchAll`은 일정·공지·연락처를 `Promise.allSettled`로 조회하고 성공한 배열만 합친다. 세 출처가 모두 실패할 때만 오류를 던진다 (`lib/api.ts:272-290`). 예를 들어 공지 조회가 실패하고 연락처 조회가 빈 배열로 성공하면, UI는 오류 대신 결과 없음 또는 불완전한 결과를 표시한다 (`app/features/home/SearchResultsView.tsx:82-101`).
- **상태:** 코드 경로로 확인했다. 운영 출처 장애를 의도적으로 만들지는 않았다.
- **조치:** 부분 실패를 결과와 함께 알리거나, 검색 완전성이 필요한 출처 실패는 오류로 처리한다.

### P2 · 공지·공모전 검색이 입력 글자마다 서버 조회를 시작함

- **근거:** `SearchBar`의 `searchOnChange`는 매 입력 이벤트에 `onSearch`를 호출한다 (`app/components/SearchBar.tsx:33-40`). 공지 목록과 공모전 목록은 그 값을 React Query 키에 즉시 반영하며, 검색어가 있으면 `staleTime: 0`이다 (`app/components/AnnouncementListPage.tsx:33-45, 62-75`, `app/features/academic/CompetitionsPageClient.tsx:57-78, 103-113`). 공지 API는 요청마다 여러 공지 배열을 합쳐 필터·정렬한다 (`lib/server/announcements.ts:52-78`). 요청 취소 신호나 입력 대기는 이 경로에 없다.
- **영향:** 빠르게 입력하면 중간 검색어마다 네트워크 요청과 서버 작업이 생긴다. 실제 지연 시간이나 비용 증가는 측정하지 않았다.
- **조치:** 목록 검색을 짧게 지연하거나 제출형으로 바꾸고, 진행 중인 이전 요청을 취소한다. 변경 전후 요청 수로 효과를 확인한다.

### P3 · 페이지 선택 드롭다운이 현재 페이지와 다른 값을 표시함

- **재현:** 운영 장학금 전체 목록 1페이지에서 페이지 선택 드롭다운은 `6`을 표시했다.
- **원인:** `<select value={currentPage}>`이지만 옵션은 `endPage` 이후 페이지만 생성한다 (`app/components/PaginationControls.tsx:61-71`). 1페이지일 때 값 `1`인 옵션이 없어 브라우저가 첫 옵션 `6`을 보여준다.
- **조치:** 현재 페이지를 옵션에 포함하거나, 드롭다운을 ‘이동할 페이지’용 비선택 컨트롤로 표시한다.

### P3 · 검색 결과 화면에 1단계 제목이 없음

- **재현:** 검색 결과의 접근성 트리에서 첫 결과 그룹 제목은 3단계 제목이고, 페이지의 1단계 제목은 없다.
- **원인:** 홈 대시보드에는 숨김 `h1`이 있지만 검색 결과 분기로 바뀌면 해당 노드가 사라진다 (`app/features/home/HomePageClient.tsx:229-248`). 결과 화면에는 검색 결과 문구만 있고 제목 태그가 없다 (`app/features/home/SearchResultsView.tsx:42-46`). 그룹은 곧바로 `h3`, 카드는 `h4`를 사용한다 (`app/components/SearchResultSection.tsx:27`, `app/components/SearchResultCard.tsx:38, 94, 126`).
- **조치:** 검색 결과에 `h1`을 두고 그룹·카드의 제목 단계를 순서대로 맞춘다.

## 운영상 확인이 필요한 위험

- **번들 대체 데이터의 시차:** Pages 데이터가 실패하면 `public/data`의 번들 데이터로 대체한다 (`lib/server/crawl-data.ts:42-51, 179-197`). 현재 번들 학사·장학금 공지 최신 날짜는 각각 2026-07-22, 2026-07-23이며, 운영 메인에는 2026-09-21 공지가 나온다. 따라서 Pages 장애 시 최신 공지가 누락될 수 있다. 장애 상황을 실제로 발생시키지는 않았으므로 현재 운영 결함으로 단정하지 않는다. 번들 갱신 주기와 대체 상태 표시를 점검해야 한다.
