기준: [사이트 점검 결과](./SITE_AUDIT_2026-09-28.md), `main`의 `2e82588`. 이 문서는 작업 순서와 완료 기준이며, 아래에 로컬 적용 결과를 기록한다.

## 적용할 동작

- 메인 검색어는 `/?search=...`로 표현한다. 로고·모바일 홈 버튼의 `/` 이동은 검색 상태를 지우고 대시보드를 보여준다. 브라우저 뒤로가기·앞으로가기와 새로고침도 URL에 맞게 동작하게 한다.
- 통합 검색은 **미리보기**로 유지한다. 현재 60건 조회를 무조건 전체 데이터 로딩으로 확대하지 않는다. 표시 수는 전체 일치 건수처럼 보이지 않게 바꾸고, 각 `전체보기`는 해당 목록에서 같은 검색어를 적용한다.
- 검색 출처 하나가 실패하면 성공한 결과는 보여주되, 빠진 출처를 명확히 알린다. 모든 출처가 실패하면 기존 오류·재시도 화면을 사용한다.
- 위 세 항목은 검색 URL·결과 표시·장애 표현에 관한 제품 동작 가정이다. 구현 전 이 계약을 기준으로 작업한다.

## 1. 검색 이동과 목록 연결 — 우선 처리

**대상:** 로고 홈 복귀(P1), `전체보기` 검색어 소실(P1), 결과 제목 구조(P3).

1. `HomePageClient`의 검색 화면 여부를 URL의 `search` 값에서 결정한다. 검색 제출은 정규화한 값을 URL에 반영하고, 검색 취소는 `search`만 제거한다. 헤더 로고와 `BottomNav`는 기존 홈 링크를 재사용한다. 언어 경로(`/en`)에서도 동일하게 적용한다.
2. `SearchResultSection`의 검색 가능한 여섯 카테고리 모두에 `search`를 전달한다. `AnnouncementListPage`, `SchedulePageClient`, `PhonePageClient`가 최초 진입과 뒤로가기 때 이를 읽어 검색창·목록에 반영한다. 목록의 검색어 삭제와 페이지 이동도 상태가 어긋나지 않도록 한다.
3. 결과 화면에 의미 있는 `h1`을 넣고 카테고리·카드 제목을 `h2`·`h3` 순서로 맞춘다.

**완료 기준:** `장학금` 검색 → 로고 또는 모바일 홈 → 대시보드 표시. 검색 → 각 `전체보기` → 검색어가 입력창과 목록에 유지. 직접 URL 접속·새로고침·뒤로가기·`/en`에서도 동일. 접근성 트리에 검색 결과 `h1`이 있다.

**최소 검증:** 홈 검색 상태와 목록 URL 초기화에 대한 컴포넌트 테스트 각 1개, 브라우저에서 로고·모바일 홈·전체보기·뒤로가기 확인.

## 2. 검색 결과의 정확성과 장애 표현

**대상:** 동일 전화번호 누락(P2), 결과 제한 오해(P2), 부분 실패 은폐(P2).

1. `lib/api.ts`의 연락처 중복 제거 키와 `SearchResultSection`의 카드 키를 부서+번호로 통일한다. 같은 번호를 공유하는 두 부서는 모두 남기고, 완전히 동일한 레코드만 제거한다.
2. 메인 검색 결과의 카테고리 숫자를 ‘전체 건수’로 읽히지 않게 한다. 검색 결과가 첫 60건·최대 100건의 미리보기라는 안내를 붙이고, 전체 탐색은 1단계에서 고친 카테고리별 목록으로 연결한다. 서버의 전체 스캔·대량 응답은 추가하지 않는다.
3. `searchAll`이 출처별 성공·실패를 반환하도록 최소한으로 조정해 결과 화면에 부분 실패 경고를 표시한다. 성공 출처가 하나도 없으면 오류로 처리한다. 재시도는 실패 출처를 다시 조회할 수 있어야 한다.

**완료 기준:** `02-3399-3239` 검색에 `학생상담센터`와 `SU인권센터`가 모두 나온다. `장학금`처럼 60건을 넘는 검색에는 미리보기 제한이 명시되고 `전체보기`에서 전체 필터 목록으로 이어진다. 공지 조회 실패와 연락처 성공을 함께 재현했을 때 ‘결과 없음’으로 단정하지 않는다.

**최소 검증:** 검색 결합 함수에 동일 번호 2건·부분 실패 1건의 단위 테스트. 60건 초과 결과의 UI 문구와 링크 테스트.

## 3. 조회 효율과 공통 UI

**대상:** 입력마다 서버 조회(P2), 잘못된 페이지 선택 값(P3).

1. 공지·공모전 목록에서 입력값과 조회값을 분리하고 짧은 입력 대기(초기값 250ms)를 둔다. 기존 `SearchBar`를 재사용하며 새 패키지는 추가하지 않는다. React Query의 취소 신호를 `fetchJson`에 전달해 이전 검색 요청을 취소한다.
2. `PaginationControls`의 `<select>`에 현재 페이지를 표시할 수 있는 옵션을 포함한다. 첫 페이지와 중간·마지막 페이지의 선택값이 실제 페이지와 일치하게 한다.

**완료 기준:** 연속 입력 시 중간 글자마다 API 요청이 발생하지 않는다. 입력 정지 후 최신 검색어 결과만 표시한다. 1페이지 드롭다운이 `6`을 현재 페이지처럼 표시하지 않는다.

**최소 검증:** 가짜 타이머로 입력 3회 후 최종 조회 1회를 확인하고, 페이지 선택 컴포넌트의 첫·중간·마지막 상태를 확인한다. 브라우저 네트워크 요청 수도 변경 전후 비교한다.

## 4. 대체 공지 데이터의 최신성

**대상:** Pages 장애 시 번들 데이터 시차(운영 위험).

1. 게시 중인 Pages manifest와 번들 공지 4개 파일의 최신 날짜·건수·해시를 비교한다. 공식 원본과 대조한 뒤 번들 갱신 경로가 최근 데이터를 포함하도록 고친다.
2. Pages 실패를 로컬에서 모의해 대체 데이터가 선택되는지 확인하고, 그때 사용자에게 번들 데이터 출처·기준일을 표시한다. 기존 데이터 상태 표시 패턴을 우선 재사용한다.

**완료 기준:** 대체 데이터의 기준일이 문서화되고, 장애 시 표시되는 공지의 최신성 한계를 알 수 있다. 실제 공식 공지와 맞지 않는 데이터를 단순 날짜 맞추기로 게시하지 않는다.

## 실행·배포 순서

1. **검색 이동·목록 연결**을 먼저 완료한다. 2단계의 ‘전체보기’가 이 경로에 의존한다.
2. **검색 정확성·장애 표현**, 그다음 **조회 효율·페이지 선택**을 변경한다. 각 단계는 관련 테스트와 브라우저 재현을 통과한 뒤 다음 단계로 간다.
3. **대체 데이터**는 공식 원본 확인 후 별도로 갱신한다. 코드 수정과 데이터 대량 변경을 섞지 않는다.
4. 최종 게이트: `npm run lint`, `npm run type-check`, 관련 단위 테스트, `npm run build`, `git diff --check`. 저장소 전체 검사는 Python 실행 경로를 지정해 나머지 Python 검사까지 완료한다. 운영 배포 뒤에는 `/`, `/en`, 공지 4종, 일정, 연락처를 다시 확인한다. 모바일 홈과 검색은 실제 모바일 화면에서 확인한다.

관리자 인증 후 기능·회의실 참여·실시간 셔틀·실기기 푸시는 이 계획의 검색 수정 범위와 독립적이며, 해당 기능을 변경할 때 별도 실행 검증이 필요하다.
